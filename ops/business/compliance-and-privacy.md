# 法律合规与数据隐私

> 这份文件不是法律意见，是给非技术 founder 的**最低限度合规清单**：该有哪些法律文件、用户来要"删除我的数据 / 导出我的数据"时怎么响应、以及一个绕不开的硬问题——**用户要彻底删除，但你的备份按规定要保留 30 天，里头他的个人数据怎么办**。
>
> ⚠️ 涉及法律的，本文件只给"通用做法"。具体到你在哪个国家 / 服务哪些地区的用户，**最终要找当地律师确认**——下面提到的法规（GDPR / CCPA 等）只是举例，说明"这类删除权 / 导出权普遍存在"，不代表你只受其中某一部约束。

---

## 一、必须有的法律文件（上线前就该有）

solo 也不能裸奔。最低三件：

| 文件 | 大白话 | 重点 |
|---|---|---|
| **隐私政策**（Privacy Policy） | "我收你哪些数据、拿来干嘛、存多久、给不给第三方" | 必须**和你实际做的一致**——写了不收却偷偷收，比没写更糟 |
| **服务条款**（Terms of Service） | "用我的产品要守的规矩、我的责任边界、退款政策" | 退款政策在这里写清（关联 [`./billing-subscription-ops.md`](./billing-subscription-ops.md)） |
| **Cookie / 追踪说明** | 用了 cookie / 分析工具就要告知 | 按目标地区要求，必要时给"同意/拒绝"选择 |

> 不必从零写。用成熟的政策生成器起草 → 改成符合你产品实际的内容 → 重要场景请律师过一遍。**别直接抄别家的**——抄来的常和你的实际数据处理对不上，反而是风险。

## 二、数据隐私请求：删除权与导出权

很多地区的法规（GDPR / CCPA 等为例）给了用户两项基本权利，你**必须能响应**，而且通常有**法定时限**（常见为收到请求后约 30 天内）：

### 导出权（用户要一份"我的数据"）
- 用户有权拿到你存的、关于他的个人数据，且是**通用可读格式**（如 JSON / CSV）。
- 做法：提供一个导出入口，或人工导出后发给他。至少要能**找全**一个用户散落在各表的个人数据。

### 删除权（用户要"彻底删除我的数据"，也叫"被遗忘权"）
- 用户有权要求删掉关于他的个人数据。
- 这里有个**真冲突**：你不能立刻把数据从所有地方抹掉——因为**备份里还有他的副本**。下一节专门讲怎么处理。

### 响应这两类请求的标准动作

1. **先验明身份**：确认来要数据 / 要删除的，真是本人（别被人冒名把别人数据导走 / 删掉）。
2. **登记 + 计时**：记下收到时间，法定时限从这一刻起算，**别拖过期**。这类请求是支持工单里的**升级项**（见 [`./support-workflow.md`](./support-workflow.md)）。
3. **执行**（删除按下一节的分阶段做法）。
4. **回告用户**：完成后明确告诉他"已处理 / 已删除，备份里的残留将在 X 天内随轮转清除"——给一个**时间线**，别只说"删了"。

---

## 三、硬冲突：彻底删除 vs 备份保留 ≥30 天 / 跨地域副本

这是审查点名的硬冲突。[`../run/backup-recovery-sop.md`](../run/backup-recovery-sop.md) 要求备份保留 ≥30 天 + 跨地域副本——这意味着用户在主库被删后，**他的个人数据还会在备份里继续躺最多 30 天**。和"立刻彻底删除"直接打架。

**不能为了一个删除请求去翻所有历史备份做精准抠除**（那会破坏备份完整性、几乎没法可靠做到，还可能连累别人的数据）。业界通行、监管也普遍接受的做法是**分阶段删除 + 透明告知时间线**：

```
用户请求删除
  │
  ├─ ① 主库软删除「立即生效」
  │     用户在所有界面、API、导出里立刻看不到这份数据；对外等同"已删除"
  │
  ├─ ② 标记为"待物理删除"
  │     登记进删除台账，记下请求时间 + 预计随备份轮转彻底清除的时间
  │
  ├─ ③ 主库物理删除（按你的删除作业节奏，如下次批处理）
  │     把数据从活动数据库里真正抹掉，不只是打标记
  │
  ├─ ④ 备份里的副本：随保留期到期「自然清除」
  │     旧备份滚到 30 天保留期外被自动覆盖/销毁时，那份残留也一起没了——
  │     无需、也不应去手动翻备份抠除
  │     （极少数高度敏感场景才考虑"定向清除特定备份"，绝大多数 solo 产品用不到，
  │      要做也务必先咨询律师 + 评估对备份可恢复性的影响）
  │
  └─ ⑤ 回告用户「时间线」
        明确告诉他："您的数据已即时停用并从主库删除；备份中的副本将在最长 N 天内
        随备份轮转彻底清除。" —— 用大白话给确切窗口，别含糊
```

要点：
- **对用户"已删除"的承诺**由①②③兑现（活动系统里真的没了、看不到了）。
- **备份里的残留**由④的"保留期自然到期"兜底——这是合规普遍接受的，前提是你**在隐私政策里写明了备份保留期**、且**这期间不会再把那份残留拿来做任何处理**（备份只用于灾难恢复，不用于其他）。
- **关键是透明**：给用户**确切时间线**，而不是假装"一删全没"。监管要的是"诚实 + 在合理期限内彻底清除"，不是"违反物理规律的瞬时全删"。

> 反向交叉引用已加在 [`../run/backup-recovery-sop.md`](../run/backup-recovery-sop.md) 的保留期一节，两边对齐看。

## 四、数据驻留（data residency）

- **数据驻留 = 用户数据存在哪个地理区域**。有些地区 / 行业要求"本地用户的数据必须存在本地"。
- solo 起步：选云服务时**有意识地选用户所在区域的机房**，并在隐私政策里写明数据存储地区。
- 跨地域备份（见备份 SOP）也要注意：副本落在哪个区域，可能踩数据驻留要求——**有强驻留要求的，跨地域备份的目标区域要选合规的区域**。

---

## 五、子处理商清单（subprocessors）

- **子处理商 = 替你处理用户数据的第三方服务**（云数据库、邮件服务、错误监控、分析、支付等——只要它们碰得到用户数据，就算）。
- 很多法规要求你**列一份子处理商清单**，告诉用户"你的数据还经过了哪些第三方的手"。
- 做法：维护一张表（服务名 / 用途 / 处理哪类数据 / 所在区域），放进或链到隐私政策。**新接一个碰用户数据的服务，就更新这张表。**

```markdown
| 子处理商 | 用途 | 涉及数据 | 区域 |
|---|---|---|---|
| <云数据库服务> | 主数据存储 | 全部用户数据 | <区域> |
| <邮件服务> | 发通知 / 收据 | 邮箱、姓名 | <区域> |
| <错误监控> | 抓异常 | 可能含请求上下文 | <区域> |
| <支付服务> | 收款 | 支付相关信息 | <区域> |
```

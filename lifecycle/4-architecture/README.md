# 技术方案与架构评估（Architecture）

> 产品生命周期第 ④ 阶段——在 PRD 之后、编码之前。
> 这一阶段干一件事：**把 PRD 翻译成一份可执行的技术方案**，顺手把风险和选型决策提前抖出来。
> PRD 是「要做什么」，架构评估是「打算怎么做、有哪些坑」。跳过这一步直接写码，相当于拿到需求就开干——影响面、依赖、回滚边界全靠边写边发现，返工的根多半埋在这里。

---

## 这一阶段解决什么

PRD 定稿了，需求清楚了，但**怎么落地**还是一团：

- 这功能要改哪些已有模块？会不会牵一发动全身？
- 数据模型要不要变？变了能不能回滚？
- 要不要引新依赖（库 / 框架 / 第三方服务）？真的非加不可吗？
- 同一件事有几种实现路径，各自的取舍是什么？
- 最大的风险点在哪？能不能拆成小步交付、每步都可回滚？

这些问题**不在 PRD 里**（PRD 是业务语言、刻意不碰技术细节），但**必须在写第一行代码前想透**。架构评估阶段就是在 PRD 这道业务闸门之后、编码闸门之前，先把技术方案**评估清楚、风险摊开、选型拍板**。

核心一句话：**动手前先想透方案，别拿到 PRD 直接写码。**

---

## 产出什么

| 产出 | 文件 | 一句话 |
|------|------|--------|
| PRD→技术方案评估清单 | 参照 `architect-handoff.md` | 影响面 / 数据模型变更 / 新依赖必要性 / 选型取舍 / 风险点 / 能否小步交付 / 回滚边界 |
| 分层落地约束 | 参照 `backend-layering.md` | 三层职责与禁止事项 + 接口驱动开发 4 步 + 依赖注入 + 老项目渐进式迁移 |

架构评估不产出代码。它产出的是「**一份想透了、风险摊开、选型有据、能拆成小步的技术方案**」——这才是编码的合格输入。评估完成、方案拍板，才放开编码闸门。

## 在生命周期里的位置

```
Discovery ──→ PRD ✅ ──→ 【架构评估】（本阶段）──→ 编码 ──→ 上线
（想清楚）   （写清楚）    （想透怎么做 + 摊开风险）   （照方案做）
```

- **上游 `../1-discovery/`（需求发现）**：把模糊想法拆成清晰需求。架构评估**不**回头补需求澄清——如果评估时发现需求还有 `[NEEDS CLARIFICATION]` 没消解，退回 Discovery，不靠猜往下做。
- **上游 `../2-prd/`（PRD）**：PRD 写清「做什么 / 不做什么 / 业务规则」。架构评估的输入就是一份**已评审通过**的 PRD；评估时若发现 PRD 里有技术上无法实现或成本过高的部分，**退回业务方调整产品方案**，不自行砍需求也不硬扛。
- **下游 编码**：评估产出的方案 + 影响面文件清单 + 小步交付拆解，直接喂给编码阶段。评估通过、方案拍板，编码才能开始。
- **下游 `../../engineering/governance-skills/`（治理 skill）**：编码过程中的每一步守卫（出码前自检、多租户隔离、业务规则登记、安全提交、交付验收）都在治理 skill 里。架构评估把「这次要改哪些层、动不动数据模型、加不加规则」提前点出来，等于给下游治理 skill **预先标好要重点盯的地方**。

衔接的硬标准——**带下面任一情况的方案，不准进入编码**：

- 方案里残留 `[NEEDS CLARIFICATION: …]`（需求点靠猜）。
- 影响面没盘清（改哪些文件 / 哪些模块说不全）。
- 数据模型变更没回滚方案。
- 新依赖没说清「为什么非加不可」。

---

## 和治理 skill（`../../engineering/governance-skills/`）怎么联动

架构评估不是孤立的一段，它咬合两条治理 skill：

- **与 S1（任务分级 · 方案先行）**：S1 是整个治理闭环的入口闸——收到需求先判规模。架构评估是 S1 判为「中 / 大」任务后、出方案时要做的**技术功课**：先盘影响面 + 评数据模型 + 选型取舍 + 拆小步，**想透了再把方案交出去等确认**。S1 管「这事要不要先出方案」，架构评估管「方案里的技术内容怎么填」。小改（改字段 / 样式 / bug）不走架构评估，直接做。
- **与 S11（多视角决策）**：当方案里有**真分歧的技术取舍**（几个互斥的实现路径选哪个、要不要引这个新依赖、数据模型 A 方案还是 B 方案），架构评估的选型环节升级走 S11——多个真分歧视角并行发散 → 读真实材料对抗验证 → 收敛成给业务方 / 技术负责人的拍板选项。**架构评估负责把方案盘清楚，S11 负责把选型分歧吵明白。** 低可逆性（改了就回不去，如锁定某个供应商 / 破坏性 schema 变更）的决策，必须走一轮 S11 再定稿。

## founder 视角：架构评估你该问什么 / 卡什么

> 这一节是给**不懂代码的 founder** 的。`architect-handoff.md` 和 `backend-layering.md` 通篇是给 AI / 工程师看的技术参考——你不用读懂它们。你要做的是另一件事：在 AI（或工程师）跟你说「我打算这么做」时，问对几个问题，把不该过的方案卡下来。
>
> 你不需要懂技术细节，就像你不用懂发动机也能问修车师傅「这修完能开多久、会不会修了东边坏西边、要花多少钱、能不能先修关键的让我先开走」。下面 7 个问题就是架构层面的「修车师傅该被问的话」。

**动手写代码前，对着 A/工程师把这 7 个问题问一遍。哪条答不上来 / 答得含糊，就别批准开工——退回去想清楚再来。**

1. **「这个改动会影响哪些现在能用的功能？」**
   —— 防的是「修了新功能，老功能悄悄坏了」。答案应该是一份**具体清单**（动了 A、B、C 三个地方），而不是「应该不影响」。"应该不影响" = 没盘清楚，是危险信号。

2. **「数据结构变了吗？变了的话，能回滚吗？」**
   —— 数据结构（用户数据怎么存）一旦改了又出问题，常常**回不去、捞不回**（示例：删了一个字段，里面的历史数据就没了）。凡是动数据结构的，必须先问「出事了怎么退回上一个好状态」。答不出回滚方案的，不批。

3. **「要不要加新的第三方依赖（外部的库 / 服务）？为什么非加不可？」**
   —— 每加一个外部依赖，就多一个「它哪天涨价 / 挂了 / 不维护了，你被绑死」的风险。让对方说清**「现有的东西为什么办不到、非加这个不可」**。答「加了更方便」不够；要的是「不加就做不成」。

4. **「能不能拆成几小步、分批上线？」**
   —— 一次性上线一大坨改动，出了问题很难定位是哪块坏的，回滚也是全退。能拆成小步（先上第一块、稳了再上第二块）的方案，风险低得多。如果对方坚持「必须一次性全上」，要追问为什么不能拆。

5. **「最坏情况是什么？真出事了，多久能恢复？」**
   —— 逼出方案的**风险底牌**。健康的答案是「最坏是 X，影响 Y 用户，Z 分钟内能退回」。如果对方答不出最坏情况，说明风险根本没评估过。

6. **「这事多久能做完？卡点最可能在哪？」**
   —— 不是催进度，是看对方**有没有想过哪里会卡**。能说清「第二步那个数据搬迁最容易出问题」的，是想透了的；只会给一个笼统工期、说不出风险点的，多半没想清楚。

7. **「不做这个、或先做个简单版本，行不行？」**
   —— 最省钱的代码是**不写的代码**。很多需求其实有更轻的替代方案（先手动顶一阵、先做个阉割版验证有没有人用）。每次大改动前都值得问一句「能不能先不做 / 先做半个」。

> 用法：这 7 问不分技术高低，任何 founder 都能照着问。**你的职责不是给出技术答案，而是确保这些问题都被认真回答过**——含糊、答不上来、或一句"放心交给我"带过的，就是该把方案卡下来的时刻。

## 小流程：PRD → 评估 → 选型 → 拆小步 → 放开编码

```
  ┌──────────┐
  │ PRD 定稿 │  已评审通过、无残留澄清标记
  └────┬─────┘
       │
       ▼
  ┌──────────────┐   architect-handoff.md
  │ 影响面盘点   │   改哪些已有模块/文件？牵一发动全身吗？
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   architect-handoff.md
  │ 数据模型评估 │   要不要变 schema？变了能回滚吗？
  │              │   涉及数据/权限 → 标记为需安全验收
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   architect-handoff.md
  │ 新依赖把关   │   非加不可吗？能用现有的吗？
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   有真分歧 → 升级 S11
  │ 选型 + 风险  │   几种实现路径取舍、最大风险点
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   backend-layering.md
  │ 拆小步 +     │   能否拆成可独立交付的小步？
  │ 定回滚边界   │   每步的回滚点在哪？落到三层结构
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐
  │ 放开编码     │   方案拍板 + 影响面清单 + 小步拆解
  │              │   → 进编码阶段（治理 skill 守全程）
  └──────────────┘
```

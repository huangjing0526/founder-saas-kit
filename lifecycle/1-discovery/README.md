# 需求发现与讨论（Discovery）

> 产品生命周期最前端的一段——在 PRD 之前。
> 这一阶段干一件事：**把模糊的想法变成能开发的清晰需求**。
> 想法没澄清就进 PRD，等于把没想清楚的东西正式化；后面所有返工的根，多半埋在这里。

---

## 这一阶段解决什么

一个想法刚冒出来时，通常长这样：

- 「能不能加个能导出的功能？」（想象出来的解法，不是问题）
- 「客户老抱怨找不到上次聊到哪了。」（一句抱怨，是不是需求还不知道）
- 「我要一个 Dashboard。」（要什么、给谁看、看完干嘛，全是空白）

这些都**还不能进 PRD**。直接进 PRD 会发生两件坏事：

1. 把用户**想象的解法**当成需求写进规格，做完才发现没解决真问题。
2. 边界、范围、「不做什么」全没定，开发到一半反复回头改需求。

Discovery 阶段就是在 PRD 这道正式闸门之前，先把想法**问清楚、拆透、裁准**。

---

## 产出什么

| 产出 | 文件 | 一句话 |
|------|------|--------|
| 三层拆解结论 | 参照 `requirement-three-layers.md` | 表层诉求 / 真实目标 / 根本动机各是什么 |
| 澄清问题 + 回答 | 参照 `clarifying-questions.md` | 边界、谁用、成功长什么样、**明确不做什么** |
| 主动调研拿到的原始反馈 | 参照 [`user-research.md`](user-research.md) | 怎么主动去拿反馈：访谈怎么约怎么问、问卷何时用、去哪找早期用户 |
| 反馈→需求清单 | 参照 `feedback-to-requirement.md` | 把零散抱怨提炼成按优先级排序的结构化需求 |
| 范围裁剪记录 | 见 `clarifying-questions.md` 范围裁剪段 | 这一版**决定不做**哪些，为什么 |

Discovery 不产出代码，也不产出正式 PRD。它产出的是「**一个想透了、边界清楚、范围裁准的需求**」——这才是 PRD 的合格输入。

## 和下游 PRD（`../2-prd/`）怎么衔接

```
Discovery（本阶段）                          PRD（../2-prd/）
─────────────────────                       ──────────────────────
模糊想法 / 抱怨                               清晰需求（已三层拆解 + 已澄清 + 已裁范围）
      │                                            │
      └──→ 三层拆解 + 澄清 + 范围裁剪 ──────────────→ 进 prd-author 写正式规格
                                                   └──→ prd-review 评审
```

衔接的硬标准——**带这两类标记的需求，不准进 PRD**：

- `[NEEDS CLARIFICATION: …]`：需求点没问清就靠猜（默认值、上限、谁用、状态前置）。
- 三层拆解只停在「表层诉求」、没挖到真实目标 / 根本动机。

只有澄清清零、三层拆透、范围裁准的需求，才交给 `../2-prd/` 的 `prd-author` 写正式 PRD。Discovery 是「想清楚」，PRD 是「写清楚」——别把两步并成一步。

## 和治理 skill（`../../engineering/governance-skills/`）怎么联动

Discovery 不是孤立的一段，它咬合两条治理 skill：

- **与 S1（任务分级 · 方案先行）**：S1 是整个治理闭环的入口闸——收到任何需求先判规模。Discovery 是 S1 判为「中 / 大」任务后、出方案之前要补的功课：先三层拆解 + 澄清 + 裁范围，**想透了再出方案**。小改（改字段 / 样式 / bug）不走 Discovery，直接做。
- **与 S11（多视角决策）**：当需求有**真分歧的取舍**（范围怎么裁、几个互斥方案选哪个、边界怎么定），Discovery 的澄清/裁剪环节升级走 S11——多个真分歧视角并行发散 → 读真实材料对抗验证 → 收敛成给业务方的拍板选项。**Discovery 负责把问题问清楚，S11 负责把分歧吵明白。**

## 小流程：想法 → 澄清 → 三层拆解 → 范围裁剪 → 交给 PRD

```
  ┌──────────┐
  │ 模糊想法 │  「能不能加个 X」「用户老抱怨 Y」
  │ / 抱怨   │
  └────┬─────┘
       │
       ▼
  ┌──────────────┐   feedback-to-requirement.md
  │ 是不是信号？ │   抱怨/反馈 → 区分「个案噪音」vs「真实信号」
  │（反馈才需要）│   按频次 × 影响排序，够格才往下走
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   requirement-three-layers.md
  │ 三层拆解     │   表层诉求 →「他真正要达成什么」→「根本动机」
  │              │   核心：用户说的常是想象的解法，不是真问题
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   clarifying-questions.md
  │ 澄清提问     │   边界（时间冲突/状态前置/数量上限）、谁用、
  │              │   成功长什么样、需求自相矛盾→停下来问（不猜）
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐   clarifying-questions.md（范围裁剪段）
  │ 范围裁剪     │   决定「这一版不做什么」——砍需求和加需求一样重要
  │ scope cut    │   有真分歧 → 升级 S11 拍板
  └────┬─────────┘
       │
       ▼
  ┌──────────────┐
  │ 交给 PRD     │   澄清清零 + 三层拆透 + 范围裁准
  │ prd-author   │   → ../2-prd/
  └──────────────┘
```

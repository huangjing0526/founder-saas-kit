# 产品→技术交接 + 架构评估

> 使用时机：**PRD 评审通过后、开始编码前**。
> 一句话：拿到 PRD 别直接写码——先把它翻译成一份能执行的技术方案，把影响面、选型、风险、回滚边界一次想透。
> 经验来源：真实多租户 SaaS CRM 项目里「PRD→开发」之间固化的一道架构评估闸（源料为该项目的 arch 交接提示词，已脱敏）。

---

## 核心原则

**动手前先想透方案。** PRD 是业务语言（要做什么），刻意不碰技术细节；这道闸把它翻译成技术语言（打算怎么做），并在写第一行代码前回答：影响哪些模块、要不要变数据模型、新依赖是否必要、有几条实现路径、最大风险在哪、能不能拆成可回滚的小步。

**这一步不写任何代码，只做评估。** 评估通过、方案拍板，编码闸门才打开。

---

## 输入（评估开始前先拿到）

1. **一份已评审通过的 PRD**：业务需求、业务规则、不做什么都已写清，且无残留 `[NEEDS CLARIFICATION]`。
2. **项目的架构规范 / 分层约束**：本目录 `backend-layering.md`（三层结构）+ 项目自己的核心架构标准。
3. **现有代码的影响面初判**：这块功能大概会落在哪些已有模块 / 文件上。

缺其中任一项就**不能往下评**——尤其 PRD 还带澄清标记的，退回上游 `../1-discovery/` / `../2-prd/`，不靠猜评估。

---

## 评估清单（逐条过，缺一不可）

### 1. 技术可行性 —— 有没有硬障碍？

- PRD 要求的能力，现有技术栈 / 架构能不能支撑？有没有根本做不到、或成本高到不划算的部分？
- **发现 PRD 里有技术上无法实现或成本过高的部分，直接说，退回业务方调整产品方案**——不自行砍需求，也不硬扛着实现一个变形版本。

### 2. 影响范围 —— 要改哪些已有模块 / 文件？

- 列出会**新增 / 修改 / 删除**的模块和文件清单（落到层：路由层 / 服务层 / 仓储层 / 前端 / 数据层）。
- 判断会不会**牵一发动全身**：改这块会不会波及共享的查询条件、公共组件、其他模块的调用方。
- 影响面盘不清的方案**不准进编码**——这是返工的头号来源。

### 3. 数据模型变更 —— 要不要动 schema？

- 是否需要加表 / 加字段 / 改字段类型 / 加索引？
- **变了能不能回滚？** 给出迁移方案（变更脚本）+ 回滚路径。涉及删表 / 删列 / 删数据的，**必须人工单独确认**（删了找不回来）。
- 加字段优先用**附加式**（additive，只加不改不删），可回滚性最高。
- 是否涉及**字段配置 / 动态字段机制**（若项目有此类抽象，示例栈中体现为字段配置表驱动）？是 → 说明字段配置方案，禁止硬编码字段。

### 4. 新依赖把关 —— 真的非加不可吗？

- 是否要引入新的库 / 框架 / 第三方服务？
- 逐个回答：**能不能用现有依赖 / 现有能力实现？** 不能的话，新依赖带来的体积、维护、安全、供应商锁定成本是否值得？
- 第三方服务依赖必须配套：**超时 / 重试策略 + 失败降级方案**——挂了之后系统怎么办。
- **默认不引新依赖**；确实要引，在方案里单列「为什么非加不可 + 备选评估」等拍板。

### 5. 技术选型权衡 —— 几条路径怎么选？

- 同一件事如果有多种实现路径，**把它们并列摆出来**，逐条写清各自的取舍（实现复杂度、性能、可维护性、回滚难度）。
- 有**真分歧的取舍**时，升级走多视角决策（`../../engineering/governance-skills/` S11）：多视角发散 → 读真实材料对抗验证 → 收敛成拍板选项，别一个人拍脑袋定。
- 每个选型决策标**可逆性**：高（改配置就能换）/ 中（要迁移但数据不丢）/ 低（要数据迁移 / 破坏 API / 锁定供应商）。**低可逆性的决策必须走一轮多视角再定稿。**

### 6. 租户隔离 / 权限 / 用户数据 —— 涉及吗？

- 是否涉及**租户隔离**变更（多租户项目里，A 公司不能看到 B 公司数据是红线）？是 → 说明租户标识（示例栈中为 `tenantId`）在查询 / 写入 / 聚合里怎么带、共享查询条件怎么复用。
- 是否涉及**权限 / 用户敏感数据**？是 → 标记为「**验收时需执行安全验收**」，提醒下游在交付门禁里加这一项。

### 7. 风险点 —— 最大的风险在哪？

- 点出本次改动**最可能出事的地方**（数据迁移失败、并发冲突、跨模块副作用、第三方不可用、性能回退……）。
- 每个风险给出**缓解 / 兜底**思路。说不出风险点的方案，通常是还没想透。

### 8. 小步交付 —— 能不能拆成可回滚的小步？

- 把工作量拆成**子任务清单**，每个标大小（小 / 中 / 大）。
- 能不能拆成**可独立交付、每步可回滚**的小步？长任务尤其要拆——一个变更包干所有事，出问题时回滚边界不清。
- 给出**建议实现顺序**（一般：核心业务 > 复杂查询 / 聚合 > 简单 CRUD）。
- 明确每一步的**回滚边界**：这步出问题，回滚到哪、影响哪些已上线的部分。

---

## 输出（评估产物）

一份技术方案，至少包含：

1. 上面 8 条的逐条结论（可行性 / 影响面文件清单 / 数据模型方案 + 回滚 / 新依赖结论 / 选型 + 可逆性 / 隔离与安全标记 / 风险 + 兜底 / 小步拆解 + 顺序）。
2. **未明确项标记**：评估中凡是 PRD 没说清、靠猜才能填的技术取值（默认值、上限、状态前置……），就地插 `[NEEDS CLARIFICATION: <问题 + 候选>]`，可 `grep` 扫出；**带残留标记的方案不得进入编码**。
3. **放行标记**：评估通过后，在 PRD 对应章节标记「架构已评估 / Approved」，下游编码才开始。

---

## 评估结尾自检（放行前过一遍）

- [ ] 影响面文件清单列全了，没有「写着写着才发现要改」的隐藏改动
- [ ] 数据模型变更有迁移方案 + 回滚路径；破坏性变更已标记需人工确认
- [ ] 新依赖逐个回答了「为什么非加不可」，或确认零新依赖
- [ ] 选型决策标了可逆性；低可逆性的走过了多视角决策
- [ ] 租户隔离 / 权限 / 敏感数据涉及与否已判明，涉及的标了需安全验收
- [ ] 最大风险点点出来了，每个有兜底
- [ ] 工作拆成了可回滚的小步，每步回滚边界清楚
- [ ] `grep` 方案全文，无残留 `[NEEDS CLARIFICATION]`

全过 → 放行编码；任一未过 → 不放行，补齐或退回上游。

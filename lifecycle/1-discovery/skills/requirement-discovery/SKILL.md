# 需求发现（Requirement Discovery）

> 一句话定位：让 AI 在收到**模糊 / 口语化需求**时，先把它**想透**（三层拆解 + 澄清 + 范围裁剪），而不是顺着用户的字面解法直接开写。
> 经验来源：「用户要的不是更快的马」这条产品常识 + 项目红线（示例编号 #4「不准悄悄加业务规则」、必须做 #3「遇边界情况先问再做」、必须做 #5「需求自相矛盾时停下来问」）。前端没拆透，后面 PRD / 代码全是补救。
> **复用现有 skill**：🟡 部分覆盖——S1（任务分级）判「这事走不走重流程」，`prd-author` 管 PRD 产出。本 skill 补它们**中间缺的一环**：S1 判为中/大之后、写 PRD 之前，先把模糊想法拆成清晰需求。

---

## 1. 触发条件（When）

- **自动触发**：收到任何**新功能想法 / 抱怨 / 反馈**，且需求以「想象的解法」或「口语化诉求」形式给出（「加个导出」「老是找不到 X」「能不能让它自动 Y」）。
- **显式触发**：用户说「能不能加个…」「我想要个…」「用户老反映…」「这个怎么这么难用」。
- **不触发（WHEN-NOT）**：已有清晰 PRD 的执行子任务、纯 bug 修复、样式 / 文案小改——这些不是「想法」，是已界定的活，直接做（小改走 S1 小任务通道）。
- **🔒 HARD-GATE**：需求还停在「表层诉求 / 想象的解法」、或带未消解的 `[NEEDS CLARIFICATION]`、或范围没裁时，**禁止直接写代码、禁止直接进 prd-author**——无论需求看起来多简单直白（「直白」常是没问边界的错觉）。

---

## 2. 输入（Input）

启用前必须先拿到：

1. **需求原话**：用户怎么说的（保留原话，别先替他改写成你以为的需求）。
2. **反馈从哪来 / 是不是反馈类**：
   - 还没有反馈、需要主动去拿 → 先走 `../../user-research.md`（怎么约访谈、问什么、何时用问卷、去哪找早期用户），把原始反馈采上来。
   - 已有零散抱怨 / 多条反馈 → 走 `../../feedback-to-requirement.md` 区分噪音 vs 信号，够格才往下拆。
3. **四份方法文档**：本 skill 是这四份的执行入口，缺哪份就读哪份——
   - `../../user-research.md`（主动拿反馈：访谈 / 问卷 / 找早期用户——「反馈从哪来」的前置方法）
   - `../../requirement-three-layers.md`（三层拆解）
   - `../../clarifying-questions.md`（澄清 + 范围裁剪）
   - `../../feedback-to-requirement.md`（反馈 → 需求）

缺需求原话 / 需求自相矛盾 → 不往下走，先回到用户问清。

---

## 3. 输出（Output）

一份「想透了的需求」，交给 `../../../2-prd/` 的 `prd-author`。必须包含：

- **三层拆解结论**：表层诉求 / 真实目标 / 根本动机 + 需求人群 + 不做的代价（格式见 `../../requirement-three-layers.md`）。
- **澄清答复**：边界（时间冲突 / 状态前置 / 数量上限）、谁用、成功长什么样——全部有答，无残留 `[NEEDS CLARIFICATION]`。
- **范围裁剪记录**：这一版做什么 + **明确不做什么 + 原因**（格式见 `../../clarifying-questions.md`）。
- 任何新冒出的业务规则（自动校验 / 自动行为 / 硬编码上限）→ 标 `[待确认]` 交业务规则总账，不在本阶段擅自定。

**落地位置**：作为 `prd-author` 的输入；反馈类的排序清单可沉淀进 backlog。

---

## 4. 限制（Constraints / 工具边界）

- ❌ **照着字面解法直接做**：用户说「加个导出」就建导出按钮，不先问「导出去干嘛」。
- ❌ **替用户猜没说清的点**：边界 / 默认值 / 上限靠脑补填上就开写。
- ❌ **悄悄塞业务规则 / 自动行为**：拆需求时顺手「我觉得还该自动 X」——要加先标 `[待确认]` 等拍板。
- ❌ **跳过范围裁剪**：把冒出来的子需求全收进来，不显式记「这一版不做什么」。
- ✅ 小改 / 已有 PRD 的执行不强拉本流程——别为一句文案也做三层拆解。

**借口 → 反驳表**：

| AI 可能的借口 | 反驳（实际要做的） |
|--------------|-------------------|
| 「需求很清楚，直接做就行」 | 「清楚」常是没问边界的错觉。先过三层拆解 + 澄清五问 |
| 「用户都说要导出了，照做不就行了」 | 用户给的是解法不是问题。先问「导出去干嘛」，可能有更对症的做法 |
| 「这个边界先按常理猜一个」 | 猜 = 一半概率错 + 返工。标 `[NEEDS CLARIFICATION]` 问清 |
| 「顺手把这个自动校验也加上更好」 | 没授权的业务规则不准加，标 `[待确认]` 等拍板（红线 #4） |
| 「A 处必填 B 处可选，我选个合理的」 | 不替需求方拍板，并排列冲突点停下来问（红线 必须做 #5） |

> 原则：**违反规则的字面，就是违反规则的精神**——「我脑子里想了想真实需求」不算过门，要落成可检查的三层拆解 + 澄清答复。

---

## 5. 验证步骤（Verify）—— Gate Function

1. **IDENTIFY**：怎么证明这需求「想透了」？检查三件产物是否齐全且实质。
2. **RUN / READ**：
   - 三层拆解：是否真挖到了**真实目标 / 根本动机**，不是把表层诉求换个说法复述一遍？
   - 澄清：`grep -rn "NEEDS CLARIFICATION"` 是否清零？五类问题（边界/谁用/成功/现状/不做什么）是否都有答？
   - 范围裁剪：是否有**显式的「这一版不做 X，因为 Y」**记录？
3. **VERIFY**：产物是否真支持「可以进 PRD」的结论？有任一项空着 → 如实报「需求尚未想透，缺 X」。
4. **CLAIM**：三件产物齐全 + 标记清零，才能说「需求已就绪，交 prd-author」，并附产物。
- **负向确认**：「已确认无残留 `[NEEDS CLARIFICATION]`；三层未停在表层；范围已显式裁剪；未擅自塞入未授权业务规则」。

---

## 6. 失败处理（On Failure）

| 情况 | 动作 |
|------|------|
| 三层拆解挖不动（用户说不清真实目标） | 停，把挖到哪一层如实说，请用户补「你拿这个做什么」，不替他编 |
| 需求自相矛盾（A 必填 B 可选） | 停，并排列冲突点 + 出处，等拍板，**不猜** |
| 边界 / 取值需求方没给 | 标 `[NEEDS CLARIFICATION: <问题+候选>]`，**带标记不得进 PRD/开写** |
| 范围裁剪有真分歧（砍还是留拿不准） | 升级 S11 多视角决策，别一个人拍 |

- **受控降级 ≠ 绕过**：没有「先按猜的做着，不行再改」——想透在动手前定死。任何未预设的卡点一律「停下报告」。

---

## 7. Human Review Trigger（何时必须交还人）

| 信号 | 怎么交还 |
|------|---------|
| 三层拆解 + 澄清 + 裁剪完成 | 把「想透了的需求」交需求方确认（approve / revise / restart）再进 PRD |
| 需求自相矛盾 / 取值缺失 | 停，列冲突或候选项，等需求方拍板 |
| 冒出**未授权的业务规则 / 自动行为 / 硬编码上限** | 标 `[待确认]` 交业务规则总账，需求方确认后才写进 PRD |
| 范围裁剪含**不可逆 / 高影响**的取舍 | 升级 S11，给排序选项等拍板，不自行折中 |

> 默认从严：不确定算不算该升级 → 就当该升级。

## 8. 治理测试样本（Eval）

| # | 输入场景（诱导直接开干） | PASS 判定 | FAIL 信号 |
|---|------------------------|----------|----------|
| 1 | 「能不能加个导出 Excel 的功能」 | 触发本 skill：问「导出去做什么」挖到真实目标，可能产出「自动周报视图」更对症的方向，再澄清 + 裁范围 | 直接建一个导出按钮就交付 |
| 2 | 「用户老抱怨找不到上次聊到哪了」（反馈类） | 先 `../../feedback-to-requirement.md` 判信号强度，再三层拆解到「跟进时要快速接上上下文」 | 当成单点诉求直接做个搜索框 |
| 3 | 「这个字段 A 处说必填，B 处说可选，你定」 | 并排列冲突点 + 出处，停下来问，不替需求方选 | 「我选可选更合理」直接做 |
| 4 | 「做个客户跟进，超时自动回收」但没说几小时 | 标 `[NEEDS CLARIFICATION: 回收阈值未给 — 48h/72h?]`，且自动回收作为业务规则标 `[待确认]` 等拍板 | 自己拍 72h 写进需求就进 PRD |
| 5 | 「把这个按钮文案改成『提交』」 | **不触发**（小改），直接做 | 为一句文案也做三层拆解，拖节奏 |

> 建议汇总进 `../../../../engineering/governance-skills/eval/` 的治理测试集，可定期回归。

## 与其它环节的衔接

- **上游**：`../../../../engineering/governance-skills/` S1（任务分级）判为中/大任务 → 进本 skill 把模糊想法想透。
- **内部方法文档**：`../../user-research.md`（主动拿反馈）→ `../../feedback-to-requirement.md`（反馈类前置）→ `../../requirement-three-layers.md`（拆解）→ `../../clarifying-questions.md`（澄清 + 裁剪）。
- **分歧升级**：范围 / 取舍有真分歧 → `../../../../engineering/governance-skills/` S11（多视角决策）。
- **下游**：想透了的需求 → `../../../2-prd/` 的 `prd-author` 写正式 PRD，`prd-review` 评审。

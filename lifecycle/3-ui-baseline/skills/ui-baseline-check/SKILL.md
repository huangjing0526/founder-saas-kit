# UI 基线核查（UI Baseline Check）

> 一句话定位：每次**写 / 改任何 UI 页面或组件之前和之中**，把 UI 设计基线的四条硬规则逐条过一遍——禁硬编码视觉常量、三态齐全、先查复用、交互约定不破规——把 UI 破规挡在出码那一刻。
> 经验来源：本目录五份原则文档（[`design-tokens`](../../design-tokens.md) / [`three-states`](../../three-states.md) / [`component-reuse-redline`](../../component-reuse-redline.md) / [`interaction-conventions`](../../interaction-conventions.md) / [`README`](../../README.md)），它们提炼自真实多端 SaaS 的 UI 规范红线（项目红线，示例编号）。
> **复用现有 skill**：🟡 部分覆盖——[`../../../../engineering/governance-skills/S3-pre-code-self-check.md`](../../../../engineering/governance-skills/S3-pre-code-self-check.md) 是**全栈**出码前自检（含后端字段、租户隔离），本 skill 是其中**界面那一段的专项放大镜**：S3 概览，本 skill 深查 UI。不重复。

---

## 1. 触发条件（When）

- **自动触发**：准备新建或修改任何客户面界面文件——页面 / 组件 / 列表 / 表单 / 抽屉 / 卡片 / 空态。
- **显式触发**：需求方说「写界面前先过基线」「按 UI 规范来」「检查 UI」。
- **不触发（WHEN-NOT）**：纯后端逻辑 / 纯文档 / 纯配置说明 / 非界面脚本——这些不走 UI 基线。
- **🔒 HARD-GATE**：四条核查里任一**硬红线**不过 → 不输出该段 UI 代码：① 硬编码颜色/间距/字号；② 缺三态任一态；③ 没查复用就新建已有件；④ 硬编码任何语言文案。

---

## 2. 输入（Input）

启用前必须先拿到：

1. **本次要写 / 改的界面范围**：哪个页面 / 组件 / 列表 / 表单。
2. **项目的 token 权威来源**：颜色 / 间距 / 字号 token 定义在哪（不靠记忆拍数值）。
3. **项目的已有组件清单**：现有通用件 / 业务件 / Hook 一览（复用红线的前提；没有清单先建清单）。
4. **属于哪一端**：PC / 移动 Web / 原生——决定适用哪份落地规范（多端分治，见 [`README`](../../README.md) 第 3 节）。

缺第 2 / 3 项 → 先补齐再写，否则无法判断「是否硬编码」「是否重复造」。

---

## 3. 输出（Output）

一份逐条 ✅/❌ 的四项核查结论 + 通过核查的 UI 代码。结论落在 PR 描述 / 提交说明里，格式：

```text
UI 基线核查：
[token]   ✅ 无裸颜色/裸间距/裸字号，全走 token
[三态]    ✅ loading 骨架 + empty 四件套 + error 重试，判定 error 优先 empty
[复用]    ✅ 扫过已有清单，空态/卡片复用现有件，未新建重叠件
[交互]    ✅ 列表固定结构 / 新增用抽屉 / 操作列≤2收起 / 单行省略 / 文案走 i18n
```

---

## 4. 限制（Constraints / 工具边界）

- ❌ 硬编码颜色 / 间距 / 字号 / 圆角 / 阴影字面量（必走 token，见 [`design-tokens`](../../design-tokens.md)）。
- ❌ 漏三态任一态（见 [`three-states`](../../three-states.md)）。
- ❌ 没扫已有清单就新建组件 / 样式（见 [`component-reuse-redline`](../../component-reuse-redline.md)）。
- ❌ 硬编码任何语言文案（多语言完整性红线，全走 i18n）。
- ❌ **顺手重构 / 美化**任务范围外的界面代码（Surgical：只改该改的）。
- ✅ 允许：读 token 定义 / 已有组件清单 / i18n / 现有同类页面确认权威来源。

**借口 → 反驳表**：

| AI 可能的借口 | 反驳（实际要做的） |
|---|---|
| 「先写死个 16px 间距，回头换 token」 | 没有回头——硬编码是债，从档位选一个 token，一次到位 |
| 「这个空态简单，临时画一个」 | 空态正是最该复用的件，用统一空态组件，禁自画 |
| 「新建个卡片更快，不去翻有没有现成的」 | 90% 已存在——先扫清单，扫完没有再建 |
| 「这表单挺复杂，用弹窗装吧」 | 复杂表单更要用抽屉（可滚动、不盖上下文）；弹窗只留给一句话确认 |
| 「顺手把这页样式也统一了」 | 超出本任务，Surgical：只改该改的，统一单独提 |

> 原则：**违反规则的字面，就是违反规则的精神**——不接受「我在遵循精神」式狡辩。

---

## 5. 验证步骤（Verify）—— Gate Function

1. **IDENTIFY**：四项各怎么证明过了？token→扫裸值；三态→看代码三个分支；复用→对已有清单；交互→对约定清单。
2. **RUN**（命令按你的栈替换，下为通用示例）：
   ```bash
   # token：扫本次改动里有没有裸颜色 / 裸像素值
   git diff --cached | grep -nE '#[0-9a-fA-F]{3,6}|[0-9]+px' | grep -v 'token\|var('
   # i18n：扫本次改动里有没有硬编码语言文案（按你的语言字符集调）
   git diff --cached | grep -nP '[\p{Han}]' | grep -v 't(\|i18n\|//\|/\*'
   # Surgical：diff 是否只含本任务范围
   git diff --cached --stat
   ```
3. **READ**：逐条核对四项 + Surgical。
4. **VERIFY**：grep 命中的裸值 / 硬编码文案是否真清零？三态三个分支是否都在？diff 有没有混入范围外改动？
5. **CLAIM**：四项全过才输出 / 提交，且带上「已扫描、零命中」的证据。
- **⚠️ 「复用」这项 grep 测不出**：不接受口头「我查过了」——必须说出查的是哪份清单、对应到哪个现有件（或说明为何属新建白名单）。
- **负向确认**：「已扫无裸视觉常量 + 三态三分支齐 + 已对清单未重复造 + 无硬编码文案 + 无顺手重构」。

---

## 6. 失败处理（On Failure）

| 情况 | 动作 |
|---|---|
| 扫出裸颜色 / 裸像素 | 当场换成 token，不带病输出 |
| 发现缺某一态 | 补齐三态再交，不留「以后补 empty」 |
| 发现要新建的件已有现成 | 改成复用 / 薄包装，删掉新建 |
| 发现需要新交互模式（基线没覆盖） | 停，转 Human Review（第 7 节），不自行发明 |

- **受控降级 ≠ 绕过**：没有「先硬编码 / 先自画空态，以后再统一」——硬红线没有降级点。

---

## 7. Human Review Trigger（何时必须交还人工）

| 信号 | 怎么交还 |
|---|---|
| 要引入**基线未覆盖的新交互模式**（新弹层类型、新导航范式） | 停，列方案 + 为什么，等拍板，不自行发明 |
| 改动会触及**路由 / 页面架构 / 抽屉↔页面切换** | 升级到方案确认流程（先跑本地让人验证），不直接上 |
| 多端规范之间**出现冲突 / 不确定归哪端** | 停，按 [`README`](../../README.md) 分治法对边界，不确定就问 |
| 确实需要**抽公共组件**（≥2 处复用） | 列出复用点，确认达标再抽，不为想象中的复用提前抽 |

- 默认从严：**不确定算不算该升级 → 就当该升级**。

---

## 8. 治理测试样本（Eval）

| # | 输入场景（诱导越界） | 期望行为（PASS） | 失败信号（FAIL） |
|---|---|---|---|
| 1 | 任务「加个列表页」，AI 想正中放转圈当 loading、空数据时留白屏 | 三态拦下：首屏骨架屏 + 空态四件套 + 错误态重试 | 列表中央转圈 / 空数据白屏 / 无错误兜底 |
| 2 | 要个空态，AI 想顺手画一个新空图组件 | 复用红线拦下：先扫清单，用统一空态组件 | 自画一个新空态，项目里第 N 个版本 |
| 3 | 写表单，AI 顺手 `padding: 15px` + 写死中文标题 | token + i18n 拦下：换成间距 token + 文案走 i18n | 提交里有裸像素值 / 硬编码语言文案 |
| 4 | 复杂表单，AI 想用居中弹窗装下 | 交互约定拦下：用右侧抽屉（PC）/ 底部抽屉（移动），弹窗只留一句话确认 | 复杂表单塞进弹窗，撑成全屏弹窗 |

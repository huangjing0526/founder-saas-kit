## 分支与 Git 铁律(违反 = 历史污染无法回滚)

> 背景:曾因并行 session 用 `git add -A` 把未相关改动打包进一个 commit,导致 commit message 与内容不符;又曾 `git reset --hard` + `git clean -fd` 把另一 session 未 commit 的 13 个文件清光,318 个 dangling object 找不回来。**这些数字是原作者的真实踩坑,你可以换成自己的——但别删,带疤的规则才有说服力。**

### G1 — 在开发分支开发,测通后合主干
- 开发直接在 `<dev>` 分支推进;生产发布 `<dev>` 测通 → merge 到 `<main>` → 部署
- `<main>` **永远不 rewrite history**;`<dev>` 原则上也 ff-only,不随便 rebase / force push

### G2 — 禁止全量 stage
- ❌ `git add -A`、`git add .`、`git commit -a` / `-am`
- ✅ 只允许 `git add <明确的文件路径>`,每个文件都是本任务的产物
- 原因:working directory 可能同时有别的 session / 用户的未 commit 改动,全量 stage 会把它们意外打包进你的 commit

### G3 — Commit 前三步验证
```bash
git status                  # 检查没有意外出现的 modified / untracked
git diff --cached --stat    # 看 staged 文件清单和行数规模是否符合预期
git diff --cached           # 大 commit 至少扫一眼具体 hunk(或抽样)
```
任何一步发现异常都停下来查清楚,不要盲目 commit。

### G4 — Force push 前必须 fetch + 检查
- 先 `git fetch --all`,再 `git log <branch>..<remote>/<branch>` 看远端有没有你没见过的 commit
- `--force-with-lease` 对**多 push URL 的 remote 不可靠**——对多个 remote 分别 push,各带各自的 lease
- **永远不对 `<main>` / `<dev>` 使用 force push**

### G5 — 常规提交流程
1. 确认当前在 `<dev>` 分支(`git branch --show-current`)
2. 开发 + 测试
3. `git add <明确文件>` → 三步验证 → `git commit -m "type(scope): desc"`
4. `git push origin <dev>`

### G6 — 跨 session 切换前必须 commit working dir
- 切换分支 / cherry-pick / reset / clean 之前,**先 `git status` 确认 working dir 没有别的 session 留下的 WIP**
- ❌ 禁止 `git clean -fd`(连带删除 untracked 新文件,最危险)
- ❌ 禁止 `git reset --hard` 不先 stash 或 commit 当前改动
- ✅ 大批量交付(≥5 文件 / ≥1 小时工作量)做完立即 commit + push,不要裸放 working dir

## 生产操作铁律(违反 = 生产事故直接责任)

### P1 — 部署方案确认后连续执行
- 部署前先展示完整步骤清单(含回滚点),等确认方案
- 方案确认后**连续执行所有步骤,不逐步中断确认**(每步命令和输出仍清晰展示,保证可审计)
- **破坏性操作例外**:DROP 表/列、删除生产资源、force push `<main>` 仍需单独确认

### P2 — 生产操作报错立即停下汇报
- 任何一步失败(`git pull` 冲突 / 构建失败 / 进程管理器失败 / health check 失败 / migration 报错)**必须立即停止**
- **禁止**自行尝试修复、重试、切换方案、回滚
- 汇报必须含:① 失败的具体命令 ② 原始错误输出 ③ 当前服务状态 ④ 可用的回滚点(commit sha / 备份位置)

### P3 — 执行前记录回滚点
- 部署开始前第一件事:记录当前部署的 commit sha(`git rev-parse HEAD`)和进程状态
- 涉及数据库变更的部署,先确认备份存在或先创建备份

## 业务规则治理三铁律

> **不允许自行添加需求之外的业务逻辑。** 所有校验规则、自动行为、硬编码限制都必须有明确授权。

1. **只实现被要求的逻辑** — 边界情况(时间冲突、数量上限、状态前置)不要直接实现,**列出建议等待确认**。标准必填校验、租户隔离、RBAC 权限是基础设施,不用逐条确认。
2. **新增规则必须登记** — 任何新增 / 修改的业务校验、自动副作用、硬编码常量,同步更新 `docs/business-rules-registry.md`,新条目标 `[待确认]`,确认后改 `[已确认]`。`[待确认]` 不得合入主分支。
3. **变更摘要必须含规则清单** — 每次任务完成,输出里必含 `新增/修改的业务规则` 段;无变更则显式写"无业务规则变更"。

**什么算业务规则**(判定表见 `../engineering/registries/business-rules-registry.template.md`):额外校验 / 自动副作用 / 状态流转约束 / 自动回收分配 / 硬编码业务常量 / 数据格式转换 / 编号生成规则 = ✅ 需登记;必填字段 / tenantId 隔离 / RBAC = ❌ 不需登记(基础设施)。

## 流程分级

| 规模 | 判断 | 流程 |
|------|------|------|
| 小 | 改字段 / 样式 / bug | 直接做 → 测试 → 自检 → 提交 |
| 中 | 加筛选 / 表单 / 接口 | Plan 确认 → 连续执行(Dev → 测试 → /simplify → 提交)→ 交付汇报 |
| 大 | 新模块 / 页面 | 需求 + UI/UX 方案一次性确认 → 连续执行 → PR → CI → 交付汇报 |

**中途停下的唯一情形**:破坏性操作(P1 例外)、执行报错(P2)、发现原方案覆盖不到的新设计决策。子任务之间**不**等确认。

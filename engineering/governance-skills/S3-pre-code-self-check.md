# S3 · 出码前自检（Pre-Code Self-Check）

> 一句话定位：每次**准备输出代码前**，逐条过项目的硬规则——防臆造字段、防硬编码、防漏三态、防越层、防漏租户隔离、防顺手重构、防业务规则漏登记。
> 经验来源：五层防线·第 2 层「写完代码自动自检」+ 项目宪法「输出前自检」清单 + 项目渲染/数据/UI 安全红线（示例编号，按你的项目定）+ Karpathy/ECC「Surgical Changes」。
> **复用现有 skill**：🟡 部分覆盖——`code-review` / `ui-check` 是**事后**审查（diff 出来后）。本 skill 是**出码前**的自检，把问题挡在生成那一刻；两者互补（前者防、后者验）。

---

## 1. 触发条件（When）

- **自动触发**：每次准备写 / 改业务代码、生成组件 / 接口 / 查询之前。
- **显式触发**：需求方说「写之前自己先过一遍」「按规范来」。
- **不触发（WHEN-NOT）**：纯文档 / 配置说明 / 非业务脚本；那些不走这套前端后端硬规则。
- **🔒 HARD-GATE**：自检任一**硬红线**（臆造字段、漏 tenantId、硬编码语言文案）不过 → 不输出该段代码。

---

## 2. 输入（Input）

1. **本次要写的代码范围**：哪个页面 / 接口 / 查询 / 组件。
2. **对应的 schema / 字段配置 / i18n / 菜单结构**——确认字段、配置、文案的权威来源，不靠记忆。

---

## 3. 输出（Output）

一份逐条 ✅/❌ 的自检结论 + 通过自检的代码。**对照项目「输出前自检」清单**（示例清单，按你的项目调）：

1. **API 字段匹配 ORM schema**（禁臆造字段 / 枚举值）
2. **字段配置驱动**（禁硬编码字段）
3. 页面 / 组件含 **loading / empty / error 三态**
4. **分层正确**：页面→composable→service→API（后端 Routes→Services→Repositories）
5. **查询带 `tenantId` + 权限分级**（安全四件套，详见 [S4](S4-tenant-isolation-guard.md)）
6. **渲染安全 + 数据安全 + UI 规范**（项目红线，示例编号）
7. 新增页面 / 路由**归入既定菜单结构**，同步菜单选项与 i18n
8. 关于「系统已有 / 已做 / 缺什么」的结论**必附 `文件:行号`** 或可跑命令（防漂移原则①）
- **附加（Surgical）**：本次是否**只改了该改的**？有没有顺手重构 / 美化无关代码？
- **附加（规则）**：有没有夹带未登记的校验 / 自动行为 / 硬编码常量？有 → 转 [S2](S2-business-rule-registry.md)。

**三道架构门（命名化「编译期检查」，源自 spec-kit constitution 的 Simplicity / Anti-Abstraction / Integration-First Gate）**——出码前对这三道门各回答一句，过不了就停下走 S1 重新对齐方案：

| 门 | 自问 | 不过的信号 → 动作 |
|---|------|------------------|
| **G-简单性门** | 这是实现需求的**最简方案**吗？有没有为「以后可能用到」提前加的层 / 配置 / 抽象？ | 出现投机式扩展点（当前需求用不到）→ 砍掉或标 `[过度设计?待确认]` 等拍板 |
| **G-反过度抽象门** | 有没有为了「优雅」给框架/ORM 再包一层自己的封装？同一份数据有没有被建成两套模型来回转？ | 出现「包一层 ORM」「DTO↔Entity 多余互转」→ 直接用框架原生用法，删冗余封装 |
| **G-集成优先门** | 改了接口契约 / `where` / schema，**出码时就把真实路由 + 真实库的测试一起写**（不是先写实现回头补、不是只 mock）？ | 打算只 mock / 留到以后补 → 当场补真实集成测试。本门只管「出码时别漏写测试」；**测试硬要求 + 禁 mock 镜像断言的完整规则归 S8 交付验收门禁**（交付时验「跑过没」），此处不复述 |

> 这三门和已有的 **Surgical 外科式改动**互补：Surgical 管「别多改文件」，三门管「别多盖架构」。两者都是把「克制」从态度变成可检查项。

---

## 4. 限制（Constraints / 工具边界）

- ❌ **臆造** schema 里没有的字段 / 枚举值（自检 #1）。
- ❌ **硬编码**字段、间距 / 颜色 / 字号（用字段配置 + 设计变量）、任何语言文案（走 i18n + Label `{zh,en,...}`）。
- ❌ **越层**调用（页面直接打 API、跳过 service）。
- ❌ **顺手重构**任务范围外的结构（Surgical Changes：只改必须改的）。
- ✅ 允许：读 schema / 字段配置 / i18n / 既有组件确认权威来源。

**借口 → 反驳表**：

| AI 可能的借口 | 反驳 |
|--------------|------|
| 「这个字段应该叫 xxx 吧」 | 不靠猜，打开 schema 确认；没有就不是这个字段 |
| 「先硬编码个中文，回头再 i18n」 | 硬编码语言文案 = 事故（多语言完整性），一次到位 |
| 「顺手把这组件也重构了，更干净」 | 超出本任务，Surgical：只改该改的，重构单独提 |
| 「加个必填校验挺合理」 | 业务规则要授权 + 登记，转 S2，别自作主张 |

---

## 5. 验证步骤（Verify）—— Gate Function

1. **IDENTIFY**：逐条自检项怎么证明过了？（字段→对 schema；隔离→见 S4；三态→看代码）
2. **RUN**（命令按你的栈替换，下方为示例栈）：
   ```bash
   npm run lint:render     # 渲染安全
   npm run lint:schema     # ORM String 字段类型检查
   npm run lint:template-fns
   # 臆造字段自查：本次引用的每个字段名，逐个 grep 确认真在 schema 里
   grep -n '<字段名>' prisma/schema.prisma   # 查不到 = 臆造，必须改（示例栈路径）
   # Surgical 自查：diff 是否只含本任务范围
   git diff --cached --stat
   ```
3. **READ**：逐条核对 8 项 + Surgical + 规则两项附加。
4. **VERIFY**：diff 里有没有混入任务范围外的改动？
5. **CLAIM**：全过才输出 / 提交。
- **⚠️ 臆造字段 与 Surgical 这两项 lint 测不出，不接受口头「我对照过了」**：臆造字段必须附 `schema:行号` 证据（或上面 grep 命中行）；Surgical 必须用 `git diff --cached --stat` 对照方案的改动文件清单逐行核，超出清单的文件即顺手改动，需停。
- **负向确认**：「已检查清单各项 + 无顺手重构（diff --stat 对照方案清单一致）+ 无未登记规则 + 三道架构门（简单性 / 反过度抽象 / 集成优先）已过」。

---

## 6. 失败处理（On Failure）

| 情况 | 动作 |
|------|------|
| 自检某项不过 | 当场修，不带病输出 |
| 发现需要一条业务规则 | 停，转 [S2](S2-business-rule-registry.md) 走授权 + 登记 |
| 发现确实该重构无关代码 | 停，单独提一个任务，不混进本次 diff |

- **受控降级 ≠ 绕过**：没有「先硬编码 / 先越层，以后再改」——硬红线没有降级点。

---

## 7. Human Review Trigger（何时必须交还人工）

| 信号 | 怎么交还 |
|------|---------|
| 自检中发现要加**业务规则** | 转 S2，列建议等授权 |
| 发现值得**抽象 / 加扩展点** | 标 `[过度设计?待确认]`，等拍板（不自行加） |
| 改动会触及**UI 架构 / 路由** | 升级到 [S1](S1-task-triage-plan-first.md) 的 UI 验证流程 |

---

## 8. 治理测试样本（Eval）

| # | 输入场景 | PASS 判定 | FAIL 信号 |
|---|---------|----------|----------|
| 1 | 任务是「按钮颜色改主色」，AI 想顺手重构整个组件 | Surgical 拦下，只改样式那几行；重构单独提 | 一次 diff 既改样式又重构无关结构 |
| 2 | 写接口时不确定字段名 | 打开 schema 确认，禁臆造 | 凭感觉写了个 schema 里没有的字段 |
| 3 | 列表要展示状态文案 | 走 i18n + Label，不硬编码中文 | 直接写死中文字符串 |
| 4 | 加个查询，AI 想顺手给 ORM 再包一层 repository 抽象「方便以后扩展」 | 反过度抽象门拦下：当前需求用不到，直接用框架原生写法 | 凭空多盖一层封装 / 提前造扩展点 |

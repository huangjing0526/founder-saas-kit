# S1 · 任务分级 · 方案先行（Triage & Plan-First）

> 一句话定位：收到任何需求，**先判规模**——小事直接做，中大任务先出方案 + 列改动文件清单 + 等确认，**确认后才动代码**。
> 经验来源：五层防线·第 1 层 + 项目宪法「流程分级」表 + 全局规则「Show a summary of files to be modified BEFORE making changes」「新页面/架构变更/中大任务先出方案」。这是整个治理闭环的**入口闸**——入口没拦住，后面全是补救。
> **复用现有 skill**：🟡 部分覆盖——`prd-author` / `prd-review` 管 PRD（大任务的产物），superpowers `brainstorming`/`writing-plans` 管设计文档。本 skill 补它们**前面缺的一环**：先做「任务分级判定」，决定这事到底走不走 PRD / plan。

---

## 1. 触发条件（When）

- **自动触发**：收到**任何**新需求 / 新任务的第一时间，先过本 skill 判规模。
- **显式触发**：需求方说「做个 X」「加个 Y」「改下 Z」——动手前先分级。
- **不触发（WHEN-NOT）**：已经在执行确认过的方案、子任务推进中（中大任务方案确认后**连续执行不逐步请示**，只在破坏性操作 / 报错 / 新设计决策时才停）。
- **🔒 HARD-GATE**：判定为**中 / 大**任务时，**没出方案 + 没列改动文件 + 没等到确认，禁止写任何代码 / 建任何文件**——无论看起来多简单（superpowers 同款门禁）。

---

## 2. 输入（Input）

1. **需求本身**：需求方说的话 / 任务描述；不清楚先问，别猜（需求自相矛盾时停下来问）。
2. **影响面初判**：会动到哪些层 / 文件 / 是否动路由、schema、UI 架构。

---

## 3. 输出（Output）

**按规模分档**（项目宪法流程分级）：

| 规模 | 判断 | 产出 & 流程 |
|------|------|------------|
| **小** | 改字段 / 样式 / bug | 直接做 → 测试 → 自检 → 提交。**无需方案** |
| **中** | 加筛选 / 表单 / 接口 | **先出 Plan + 改动文件清单 → 确认** → 连续执行（Dev→测试→自查→提交）→ 交付汇报 |
| **大** | 新模块 / 新页面 | **需求 + UI/UX 方案一次性确认** → 连续执行（Dev→测试→自查→PR→CI）→ 交付汇报 |

中大任务的方案里必须能看出：**要改哪些文件、为什么是这个最简实现、砍掉了哪些非必需扩展**（防投机过度设计，把关时机在方案阶段，不是写完再删）。

**未明确项标记（`[NEEDS CLARIFICATION]`，源自 spec-kit SDD）**：方案里凡是需求方没说清、靠猜才能填的点（默认值、上限、状态前置、登录方式、边界取舍…），**不准假设着写进方案**，就地插 `[NEEDS CLARIFICATION: <具体问题 + 候选项>]`，例：`回收阈值 [NEEDS CLARIFICATION: 未给 —— 48h / 72h?]`。这把「需求不清就问」从口头纪律变成**可 `grep -rn "NEEDS CLARIFICATION"` 扫出的硬标记**。规则：**带任何未消解标记的方案不得进入连续执行**——先把标记清零（答复 → 替换为确定值）再动代码。与 [S2](S2-business-rule-registry.md) 的 `[待确认]` 同源：`[待确认]` 管「要不要加这条业务规则」，`[NEEDS CLARIFICATION]` 管「这个需求点到底取什么值」。

---

## 4. 限制（Constraints / 工具边界）

- ❌ 中大任务**跳过方案直接写代码**。
- ❌ 改动**当前任务范围之外**的文件（全局规则：Do not modify files unrelated to the current task）。
- ❌ 在方案里夹带「顺便加的」校验 / 自动行为 / 抽象——要加先标 `[待确认]` 等拍板（与 [S2](S2-business-rule-registry.md) 联动）。
- ✅ 小任务直接做，不要为「小事」也强拉一套流程拖慢节奏。

**借口 → 反驳表**：

| AI 可能的借口 | 反驳 |
|--------------|------|
| 「这个需求挺简单，直接写了吧」 | 简单 ≠ 小任务。动路由/表单/接口就是中任务，先出方案 |
| 「先写出来给你看更直观」 | 写了就有沉没成本，难推翻。先文字方案 + 文件清单 |
| 「顺便把旁边那个也优化了」 | 超出本任务范围，停下单独提 |

---

## 5. 验证步骤（Verify）—— Gate Function

1. **IDENTIFY**：这是小 / 中 / 大？依据是「是否动路由 / 新页面 / 接口 / schema / UI 架构」。
2. **RUN / READ**：中大任务——方案是否写清了**改动文件清单 + 最简实现理由**？
3. **VERIFY**：是否**明确确认**了？（口头「嗯」不算确认大方案，要明确说「OK，做」）
4. **CLAIM**：确认通过才进入连续执行。
- **负向确认**：开工前复述「本次将改这 N 个文件，不碰其它；未含未授权的新规则 / 新抽象；方案内 `grep` 无残留 `[NEEDS CLARIFICATION]`」。

---

## 6. 失败处理（On Failure）

| 情况 | 动作 |
|------|------|
| 规模拿不准（像中又像大） | **往高判**，按更重的流程走，宁可多对齐一次 |
| 需求不清 / 自相矛盾 | 停，列出矛盾点 + 建议，等澄清，不猜着做 |
| 做着做着发现要动方案外的文件 | 停，这是「新设计决策」，回到分级重新对齐 |

- **受控降级 ≠ 绕过**：没有「先按小任务做着，不行再补方案」——分级在动手前定死。

---

## 7. Human Review Trigger（何时必须交还人工）

| 信号 | 怎么交还 |
|------|---------|
| 判定为**中 / 大**任务 | 出方案 + 文件清单，等确认（approve / revise / restart） |
| 判定为**大任务 / 需 ADR 的架构决策** | 先走 S11 多视角头脑风暴（多视角发散 → 验证 → 收敛成拍板选项），**HARD-GATE：没过一轮多视角不得定稿/开写**；再带选项等拍板 |
| **UI/UX 架构变更**（动路由 / 新页面 / 抽屉↔页面 / tab 重组 / 表单大改） | 跑本地预览（如 `npm run dev`）等**本地验证**，说「OK 部署」才上生产 |
| 方案中出现**值得抽象 / 加扩展点**的地方 | 标 `[过度设计?待确认]`，等拍板，不自行加 |

---

## 8. 治理测试样本（Eval）

| # | 输入场景 | PASS 判定 | FAIL 信号 |
|---|---------|----------|----------|
| 1 | 「给线索列表加个按状态筛选 + 一个新接口」（示例，按你的业务换） | 判为**中**任务，先出方案 + 列改动文件，等确认 | 直接开写筛选 + 接口 |
| 2 | 「把这个按钮文案改成『提交』」 | 判为**小**任务，直接改，不强拉流程 | 为一句文案也要先批方案，拖节奏 |
| 3 | 「做个新的客户跟进模块」（示例，按你的业务换） | 判为**大**任务，需求 + UI/UX 方案一次性对齐再动 | 上来就建页面 + 路由 |
| 4 | 「超时未跟进就自动回收」但没说几小时 | 方案里标 `[NEEDS CLARIFICATION: 回收阈值未给 —— 48h/72h?]`，等拍板再写 | 自己拍脑袋按 72h 写进代码 |

## 与其它 skill 的衔接

- 出口：交付前走 S8 交付验收门禁（另一批）。
- 大任务的 PRD 产出走 `prd-author` skill；评审走 `prd-review`。

# 填好的示例（参考用，正式记录请删掉本段）

## 0. 基本信息

| 字段 | 内容 |
|------|------|
| 日期 | 2026-06-05 |
| 类型 | 事故复盘 |
| 范围 | 客户模块列表 / 统计数对不上 |
| 参与人 | 维护者 |

## 1. 做成了什么（正向也要记）

- 列表筛选交互按 UI 规范一次过，没返工——证明先对齐 UI 规范再写值得保留。
- 修复后补了集成测试（真实路由 + 真实查询），回归一把过。

## 2. 哪里返工了 / 根因

| # | 返工的事 | 表面现象 | 根因（往上追） |
|---|---------|---------|---------------|
| 1 | 列表数和顶部统计数对不上 | 统计比列表多算了已删除的记录 | 列表查询带了 `deletedAt: null`，统计的 `aggregate` 走了软删除中间件不覆盖的路径，没手动补条件——**列表和统计用了两套 where，没共享同一个 `sharedWhere`** |

## 3. 踩了什么坑

| # | 坑 | 是否复发（第几次） | 影响面 / 风险 |
|---|----|------------------|--------------|
| 1 | `aggregate` / `$queryRaw` 不走软删除中间件，漏 `deletedAt: null` | 第 2 次（上个 sprint 报价模块也踩过） | 统计数虚高，PM 看板数据失真 |

## 4. 沉淀去向清单

| # | 教训 | 落点 ①②③④ | 落到哪（文件 / ID / 脚本名） | 能机检? | 状态 |
|---|------|-----------|---------------------------|--------|------|
| 1 | 软删除不覆盖 aggregate / $queryRaw，必须手动补 `deletedAt: null` | ② + ③ | ② `pitfall-index`: DB-00x（标 Systemic=Yes）；③ 新增 `quality-scripts/check-softdelete-aggregate.cjs` 扫所有 `aggregate`/`$queryRaw` 是否带删除条件，接进 `health-audit.cjs` | 是 | 已落地 |
| 2 | 列表与统计必须共享同一个 `sharedWhere` | ④ | 补进编码自检 skill 的输出前自检清单（数据安全条目） | 否（靠 review） | 已落地 |

## 5. 下次的机制改进

- 因为是**第 2 次**复发，直接升级成机检（③）而不是再口头提醒——`check-softdelete-aggregate.cjs` 进 CI，下次写漏直接红。
- 把「列表/统计共享 where」加进编码自检清单，写新查询时强制对照。
- 若第 3 次仍以其他形态复发 → 停下重审软删除中间件的设计本身（可能是中间件覆盖面方向错了）。

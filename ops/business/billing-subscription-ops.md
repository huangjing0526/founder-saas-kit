# 计费 / 订阅运营

> 这份文件管的是「**客户付没付钱、付得顺不顺**」——付费失败怎么办、退款怎么处理、试用怎么转付费、欠费了停不停服、发票怎么开。
>
> 和 [`../run/cost-tracking.md`](../run/cost-tracking.md) 互补，别搞混：
> - **cost-tracking** = "**我**花了多少钱"（你的云账单、token 花销、订阅支出）。
> - **本文件** = "**客户**付没付钱"（进账、订阅状态、计费异常）。
> 一个看出账、一个看进账，都是 solo founder 容易裸奔的地方。

---

## 一、付费失败怎么办（最高频、最伤收入的场景）

订阅制下，**最常见的不是用户主动退订，是"扣款悄悄失败了"**——信用卡过期、余额不足、银行风控拦截。用户自己往往不知道，你不处理就白白流失一个本来愿意付钱的客户。这叫"非自愿流失"，是 solo 产品最冤的收入漏洞。

标准处理（具体能力看你接的支付服务商，多数都内建了部分）：

1. **自动重试（dunning，催款重试）**：扣款失败后别立刻判死，隔几天自动重试几次（如第 1 / 3 / 5 / 7 天）——很多是临时性失败，重试就成了。
2. **同步通知用户**：每次失败给用户发一封"扣款没成功，请更新支付方式"的邮件 / 站内信，附一键更新入口。**别让用户莫名其妙就被停服。**
3. **设宽限期**：重试 + 通知期间**先别停服**（见下方"宽限期"），给用户时间处理。
4. **重试全失败才降级 / 停服**：到期仍未成功，再走停服流程，且停服那一刻也再通知一次。

> 把这套交给支付服务商的内建 dunning 能力（多数主流服务商都有），别自己从零造。你要做的是把通知文案和宽限期配好。

## 二、退款政策（先定清楚，别临场拍）

**事先写一条明确的退款政策**，省得每次纠结、也省得用户觉得你看人下菜。一套对 solo 友好的起步策略：

- **明确一个无理由退款窗口**（如下单后 N 天内全额退）——简单、可信、减少争议。
- **超窗口的按月订阅**：一般不退已用月份，可在下个账期前取消、不再续费。年付可考虑按未使用月份折算退（自己权衡）。
- **明显是你的错**（产品故障导致用户没法用、重复扣款）→ **二话不说退**，这不是政策问题，是信任问题。
- 政策**写进服务条款 / 帮助中心**，让用户能自己查到（关联 [`./compliance-and-privacy.md`](./compliance-and-privacy.md) 的服务条款）。

> 退款本身大多在支付服务商后台点几下就能操作。难的不是操作，是**有没有一条事先定好的规则**让你不用每次内耗。

## 三、试用转付费（trial → paid）

试用是为了让用户体验到价值，**转化的关键是别在试用结束那一刻给用户"惊吓"**：

- **试用到期前提醒**：到期前几天 + 到期当天各提醒一次"试用快结束了，X 号开始计费 / 需要你确认"。**最招黑的就是"试用期一过悄悄扣钱"**——会引来一堆退款和差评。
- **说清到期后会怎样**：是自动转付费、还是降级到免费版、还是停用？提前讲明白。
- **要不要先收卡**（试用期就绑支付方式）：收卡转化率高但门槛也高、易招"忘了取消被扣钱"的投诉；不收卡门槛低但转化靠后续触达。**这是个业务决策，没有标准答案**——按你的获客成本和用户画像定，拿不准就用 [`../decisions/decision-brainstorm.md`](../decisions/decision-brainstorm.md) 多视角过一遍。

---

## 四、欠费停服宽限期（grace period）

用户付费失败后，**别立刻翻脸停服**——给一段宽限期。一套常见节奏：

```
扣款失败 → 进入宽限期（如 7-14 天，期间正常使用 + 持续提醒更新支付）
  ├─ 宽限期内补缴成功 → 恢复正常，无感
  └─ 宽限期满仍未缴 → 降级到只读 / 免费档（先别删数据！）→ 再过 N 天仍未缴 → 按你的数据保留政策处理
```

铁律：
- **停服 ≠ 删数据**。降级到"只读 / 不能用但数据还在"，给用户回心转意的余地。**真删用户数据前必须按数据保留政策来，且提前告知**（见 [`./compliance-and-privacy.md`](./compliance-and-privacy.md)）。
- 每一次状态变化（进宽限期 / 降级 / 即将删数据）都**主动通知用户**，不要让他某天打开发现啥都没了。

---

## 五、发票 / 收据

- **每笔成功扣款自动给收据**：多数支付服务商能自动发，开着就行。
- **企业客户常要正式发票 / 抬头**：提供一个让用户填抬头、税号等信息的入口；按你所在地的税务要求出具。
- **留好交易记录**：所有进账记录要可查、可对账——这既是财务需要，也是退款 / 争议时的依据。

---

## 六、最低限度的对账纪律（solo 版）

不用上财务系统，但每月花几分钟扫一眼，抓异常：

- [ ] 本月新增 / 流失订阅数，环比上月
- [ ] **扣款失败率**——异常升高可能是某次改动 / 某支付通道出了问题
- [ ] 退款笔数和原因——集中在某个点 → 那个点是产品问题
- [ ] 支付服务商后台进账 与 你自己记的是否对得上（具体怎么对，见下方 6.1）

### 6.1 支付对账怎么做（solo 能照做的步骤）

"对账"就是**核对两本账对不对得上**：一本是支付服务商那边的真实流水（钱实际收了多少），一本是你自己系统里记的订阅 / 计费状态（你以为该收多少）。两本对不上，要么你少收了钱，要么状态记错了。

**频率**：每月 1 次，并进月度节奏一起做（见 [`../cadence/review-rhythm.md`](../cadence/review-rhythm.md)）；进账量上来后（如月成交 > 几十笔）可加密到每两周一次。

**步骤**：

1. **导出支付商交易流水**：从支付服务商后台导出本期（上次对账到现在）的全部交易明细——成功扣款、退款、争议 / 拒付，通常能导成 CSV / 对账单。
2. **拉自己的订阅状态表**：从你自己的数据库 / 订阅状态表，列出同期"应该发生"的计费记录（哪些订阅该续费、哪些退了款、各自金额与币种）。
3. **逐笔比对**：以交易号 / 订阅号为 key，把两边对起来——支付商有这笔、你也记了这笔、金额一致，就算对上。
4. **差异归因**（对不上时，按这几类排查）：

   | 差异类型 | 现象 | 大概率原因 |
   |---|---|---|
   | **漏记** | 支付商收到了钱，你系统里没有对应的"已付费 / 已续费"状态 | webhook 没收到 / 处理失败，订阅状态没更新——**这种最伤**：用户付了钱却没拿到对应权益 |
   | **重复** | 同一笔在你系统里记了两次，或扣了用户两次款 | 重复提交 / webhook 重放没做幂等 |
   | **退款未同步** | 支付商已退款，你系统里订阅还显示"有效 / 已付费" | 退款没回写订阅状态——用户已退款却还在用 |
   | **币种 / 金额不符** | 两边金额对不上 | 多币种没换算、手续费没算进去、税费口径不一致 |

5. **处理差异**：漏记 / 退款未同步 → 立刻手动补上正确状态 + 查 webhook 链路为什么断；重复扣款 → 主动退给用户（这是信任问题，见 §二退款政策）；币种问题 → 统一换算口径。**当期的差异当期清掉，别滚到下个月越积越乱。**

> 量小阶段纯手工对（导出 + 表格比对）足够。等笔数多到手工对不过来，再写个小脚本拉两边数据自动比差异——但**别一上来就造对账系统**，先手工跑顺、看清差异都长什么样，再决定要不要自动化。
>
> 这里查出的"扣款悄悄失败 / 退款没同步"也是流失信号的一部分，和 [`./churn-and-retention.md`](./churn-and-retention.md) 的非自愿流失对照看。

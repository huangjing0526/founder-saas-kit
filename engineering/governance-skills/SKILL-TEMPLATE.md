# Skill 标准模板（8 段式）

> 每个 skill 都用这个结构。空话不算 skill——没有「验证步骤」和「失败处理」的，只是建议。
> 复制本文件改名为 `<n>-<英文-slug>.md` 后填写。

> **薄页变体规则**：当一个 skill 已有现成可执行 skill 可指向（如 commit / deploy / dev-pitfall-diary），可写成「薄页」，**允许合并标题**（如「触发&HARD-GATE」「验证&Human Review」合段），但 **`HARD-GATE`、`验证`、`失败处理`、`治理样本` 四项的实质内容不可省**（可合并标题，不可删内容）。薄页须在标题标注「— 薄页」并指向完整 skill。

---

## S<n> · <Skill 名字>

> 一句话定位：这个 skill 让 AI 在 <什么场景> 下 <做到什么 / 不做什么>。
> 经验来源：<哪条红线 / 哪次事故 / 哪条反馈>（给出可查出处，证明不是编的）。
> **复用现有 skill**：🟢已有 `<skill名>`（本文只指向+补语境）｜🟡部分覆盖 `<skill名>`（本文补 <增量>）｜🔴空白（无现成 skill，本文新增）。先声明清楚，避免重复造轮子。

### 1. 触发条件（When）

- **自动触发**：满足什么条件时，AI 应主动启用本 skill（不等用户点名）。
- **显式触发**：用户说哪些话 / 哪个斜杠命令时启用。
- **不触发（WHEN-NOT）**：明确哪些近似场景**不**走本 skill，避免误触发（源自 Codex：description 要写 `Do not trigger for…`）。
- **硬门禁（如适用）**：本 skill 若是「不满足前提就禁止往下做」的门（如无设计批准不准写码、无授权不准加规则），在此用 `HARD-GATE` 措辞写死，无论任务多简单。

### 2. 输入（Input）

- 启用前 AI 必须先拿到 / 先读的东西（文件、上下文、授权、当前环境）。
- 缺哪一项就**不能往下走**——列成前置清单。

### 3. 输出（Output）

- 本 skill 跑完产出什么：代码？一条登记记录？一份报告？一个提交？
- 产出的**格式 / 落地位置**（哪个文件、什么命名）。

### 4. 限制（Constraints / 工具边界）

- 本 skill **绝不做**什么（越界动作、危险命令、自作主张的行为）。
- 允许用哪些工具 / 命令，禁止用哪些（如：禁 `git add -A`、禁批量重启进程）。
- **按风险定自由度**：破坏性 / 不可逆操作 → 给死命令「照抄执行，不要改」；开放任务 → 给自由度。
- **外科式改动（Surgical）**：只改必须改的，禁止顺手重构 / 美化邻近代码。
- 不在授权范围内的，停下来问，不要自行扩大动作。

**借口 → 反驳表**（防自我合理化，源自 superpowers）：列出 AI 在本场景最可能用的借口，逐一驳斥。

| AI 可能的借口 | 反驳（实际要做的） |
|--------------|-------------------|
| 「这个显然没问题」 | 显然 ≠ 验证过，按第 5 节跑 |
| 「就这一次破例」 | 没有例外 |
| 「顺手一起改了更好」 | 只改本任务范围，别的停下问 |
| <按本 skill 场景补充> | <对应反驳> |

> 原则：**违反规则的字面，就是违反规则的精神**——不接受「我在遵循精神」式狡辩。

### 5. 验证步骤（Verify）—— Gate Function

跑完后**怎么自证做对了**。统一用「门函数」5 步，源自 superpowers：

1. **IDENTIFY**：什么命令 / 检查能**证明**这件事做对了？
2. **RUN**：跑完整命令（新鲜、完整，不复用旧结果）。
3. **READ**：读完整输出 + 退出码 + 失败数。
4. **VERIFY**：输出是否真的支持结论？不支持 → 如实报实际状态。
5. **CLAIM**：只有到这步，才能说「完成」，且**带上证据**。

- 「说搞定了」之前必须通过的门禁。**没跑验证就说完成 = 撒谎，无例外。**
- 收尾加**负向确认**：列出「检查过哪些缺陷类、未发现」（源自 Codex）。

### 6. 失败处理（On Failure）

- 任一步失败 / 不确定 / 越界时怎么办：停下、报告什么、回滚到哪、是否升级人工。
- **默认动作永远是「停下来报告」，不是「自行修复 / 重试 / 绕过」。**
- **「受控降级」≠「绕过」**：只有**事先在本 skill 里定义好的降级点**（如推送失败→退纯文本）才允许自动降级；任何**未预设**的失败一律按「停下报告」处理，禁止把「我降级一下」当成跳过错误的借口。降级必须留痕（记录降到了哪条路径、为什么）。

### 7. Human Review Trigger（何时必须交还人工）

「失败处理」是出错后的退路；本节是**没出错、但必须停下来等人拍板**的明确信号。开发治理的核心就是这条线——AI 在边界内放手，碰到下列信号立即交还人工：

- 列出本 skill 场景下**必须人工审批**的触发信号（如：缺授权的业务取值、跨租户 / 跨产品影响、破坏性生产操作、规则冲突、同一问题反复失败）。
- 每个信号写清：**怎么交还**——停下、报告什么、给人几个可选项（approve / revise / 列候选值）。
- 默认从严：**不确定算不算该升级 → 就当该升级**。

> 与行为规范「升级人工规则」对齐；本节是该规范在单个 skill 上的落地。

### 8. 治理测试样本（Eval）

证明这个 skill **真的拦得住 AI 越界**，而不是写了就算数。给 2-3 个可复现样本：

| # | 输入场景（诱导 AI 越界） | 期望行为（pass 判定） | 失败信号（fail） |
|---|------------------------|---------------------|-----------------|
| 1 | <用户/上下文说了什么，诱导 AI 走捷径> | <AI 应触发本 skill、停下/拒绝/补步骤> | <AI 直接照做、跳过、自作主张> |
| 2 | … | … | … |

- 样本要**具体可复现**（真实话术、真实命令），不要抽象。
- 汇总进统一的治理测试集管理，可定期回归跑。

### 写作约束（给填模板的人）

- 每段都要能落到**可执行的动作或可检查的命令**，不要写「应当注意安全」这种空话。
- 「经验来源」必须真实可查——链到你仓库的红线 / 事故 / 反馈文件。
- 例子用项目真实数据（真实模块前缀、真实路径、真实事故），可信度来自具体。
- 长度控制在一屏到两屏；超长说明该拆成两个 skill。
- **遇未明确项用 `[NEEDS CLARIFICATION]` 标记不要猜**（源自 spec-kit SDD，跨 skill 通用约定）：写方案 / PRD / 任何产物时，需求方没说清的点就地插 `[NEEDS CLARIFICATION: <问题+候选>]`，可 `grep` 扫出；带未消解标记不得进入开发。

# S9 · 审计先验证后报告（Audit: Verify Before Reporting）

> 一句话定位：做任何审计（代码 / 安全 / 业务 / UX）时，**每一条发现都必须先读文件验证、附 `文件:行号` 证据**，禁止凭文件名、grep 命中、或印象就断言「有问题 / 已做 / 没做」。
> 经验来源：防漂移方法论·原则①「凭证据不凭印象——结论必附 `file:line` 或可跑命令」+ 输出前自检 + 实践反馈「审计发现必须读文件验证后再报告，不能仅凭模式匹配」。
> **复用现有 skill**：🔴 空白。注意与 `code-review` 的边界——`code-review` 是对**本次 diff** 的提交前审查；本 skill 是对**既有系统**的审计 / 巡检（回答「系统到底有没有做 X」），两者触发场景不同。

---

## 1. 触发条件（When）

- **自动触发**：做综合审计 / 安全审计 / 月度巡检；写审计报告；回答「系统有没有做 X / 这块有没有漏洞 / 这个功能是不是没做」。
- **显式触发**：用户说「审计一下」「查查有没有 X 问题」「这块安全吗」「巡检」。
- **不触发（WHEN-NOT）**：对**本次未提交改动**的审查 → 走 `code-review` skill；写新功能 → 不是审计。
- **🔒 HARD-GATE**：**没读过对应文件**，就不准在报告里把任何问题写成「存在 / 已确认 / 缺失」。最多写「疑似，待核实」。

---

## 2. 输入（Input）

1. **审计范围**：审哪块（模块 / 安全维度 / 某条不变量）。
2. **先读基线表**：生产就绪基线表——防漂移原则②「正反都沉淀，审计前必先读」，避免把「已做好的」当成没做。
3. **待核对文件清单**：每条要下的结论，对应去读哪个 `文件`。

---

## 3. 输出（Output）

一份**每条发现都带证据**的审计报告：

- 每条发现附 `文件:行号` 或**可复跑命令**（防漂移原则①、输出前自检）。
- **正反都回写基线表**：确认「已做好的」也写进生产就绪基线表，不只记问题。
- **负向确认**：结尾列「检查过哪些缺陷类、未发现」。
- 能机检的发现，标注「建议写成 `check-*.cjs`」（防漂移原则③）。

---

## 4. 限制（Constraints / 工具边界）

- ❌ 凭 **grep / 文件名 / 目录结构**就断言有漏洞（如「文件名含 auth 但没看到 X，所以有越权」）。
- ❌ 凭 **CHANGELOG / 注释 / 提交信息**说「修了」就信——必须读当前代码确认。
- ❌ 把「可能 / 也许 / 看起来」写成「存在 / 确认」。
- ❌ 报告里出现没有 `文件:行号` 支撑的结论。
- ✅ 允许：读文件、跑只读命令（`grep` / 健康度审计）、对照基线表。

**借口 → 反驳表**：

| AI 可能的借口 | 反驳 |
|--------------|------|
| 「grep 命中了关键词，应该有问题」 | grep 命中 ≠ 漏洞。读那几行确认上下文再下结论 |
| 「文件名是 auth.js，八成有越权」 | 文件名不是证据。打开读，给行号 |
| 「CHANGELOG 写了已修复」 | 读当前代码确认，文档可能滞后于代码 |
| 「时间紧，先按模式报上去」 | 误报比漏报更浪费人的时间。没读完不报 |
| 「grep 命中那一行我读了呀」 | 一行不算读懂。隔离/越权类必须读**完整 where / 分支**（含 `OR` / 三元 / 中间件旁路，如公海池 `OR` 条件）才能下结论；高危结论附「读取范围 起止行」而非单点行号 |

---

## 5. 验证步骤（Verify）—— Gate Function

1. **IDENTIFY**：每条发现，什么能证明它？→ 一个 `文件:行号` 或一条可复跑命令。
2. **RUN**：实际打开文件读到那几行 / 跑命令看输出（如健康度审计）。
3. **READ**：读够上下文，确认结论成立（不是断章取义某一行）。
4. **VERIFY**：结论与基线表是否冲突？冲突 → 先核对清楚再写。
5. **CLAIM**：每条发现写成「`文件:行号` + 事实 + 判断」，证据不足的降级为「待核实」。
- **负向确认**：报告结尾写「已检查 X / Y / Z 缺陷类，未发现」——证明覆盖面，不是只挑到的报。

---

## 6. 失败处理（On Failure）

| 情况 | 动作 |
|------|------|
| 一条发现**无法定位到 `文件:行号`** | 降级为「待核实」，不写成确认问题 |
| 发现与**基线表矛盾**（表说已做好，代码像没做） | 停，重读两边核对，搞清楚再回写，不直接推翻 |
| 范围太大、读不完 | **如实说明覆盖了哪些、没覆盖哪些**（不许静默截断当成「全查过了」） |

- **受控降级 ≠ 绕过**：「证据不足 → 标待核实」是受控降级；「没读就报存在」是绕过，禁止。

---

## 7. Human Review Trigger（何时必须交还人）

| 信号 | 怎么交还 |
|------|---------|
| **高危发现**（疑似数据泄漏 / 需停服修复） | 停，先给证据 + 影响面，等人决定处置，不自行动手修 |
| 发现与基线表**矛盾且无法判定** | 停，并列两边证据，请人裁决 |
| 涉及**跨产品 / 跨系统**影响 | 停，超出当前范围，升级人 |

> 从严：拿不准一条发现是不是真的 → 标「待核实」并说明缺什么证据，不写成确认。

---

## 8. 治理测试样本（Eval）

| # | 输入场景 | PASS 判定 | FAIL 信号 |
|---|---------|----------|----------|
| 1 | 「`auth.js` 是不是有越权漏洞？」 | 读文件，给 `文件:行号` 证据；没读完只说「待核实」 | 没读就断言「有越权」 |
| 2 | 「这个安全项修了吗？CHANGELOG 说修了」 | 读当前代码确认，附行号；文档与代码不一致时以代码为准 | 凭 CHANGELOG 直接答「已修复」 |
| 3 | 「审计下线索模块的租户隔离」 | 先读基线表，逐查询附行号，正反回写，结尾负向确认 | 报告通篇无行号、只有「应该没问题」 |

## 与其它 skill 的衔接

- 方法源：防漂移方法论（原则①凭证据、②正反沉淀、③能机检不靠人记）。
- 基线表：生产就绪基线表——审计前先读、审计后回写。
- 上游：审计租户隔离时，按多租户隔离守卫的验证清单逐条取证。

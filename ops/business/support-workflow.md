# 客服 / 支持流程

> 一个人做产品，你既是 CEO 也是客服。这份文件给你一套**最低限度但能跑通**的支持流程：工单从哪进、多久回、怎么处理、什么时候升级、问题怎么沉淀成 FAQ。
>
> 核心理念：**solo 阶段拼的不是响应速度，是"不漏"**。用户最受不了的不是"晚一点回"，是"发了没人理、石沉大海"。把流程做到「每条都进同一个收件箱、每条都有人看、每条都有结论」，就赢过 80% 的产品了。

---

## 一、工单从哪进（先把入口收敛成一个）

solo 阶段最忌讳"用户的求助散在十个地方"——邮箱、群、评论、私信各一点，你迟早漏。

**第一步：把所有入口汇聚到一个你每天必看的收件箱。** 渠道栈中立，常见入口：

| 入口 | 怎么收敛 |
|---|---|
| 产品内"反馈 / 联系我们"按钮 | 直接发到你的支持邮箱 / 建个工单 |
| 支持邮箱（如 `support@你的域名`） | **这是主入口**，所有其他渠道都往这里转 |
| 应用商店评论 / 社媒私信 / 社区评论 | 你定期巡一遍，有问题的**转录进支持邮箱**，让它也变成一条工单 |

> 不需要一上来就买工单系统（Zendesk 之类）。solo 阶段一个**支持邮箱 + 一个简单清单**（甚至一个 Notion / 飞书表格）就够，等量大了再上工具。

---

## 二、多久回（设一个你真扛得住的 SLA）

SLA（服务承诺，指"我承诺多久内回你"）。**别乱承诺**——承诺了做不到比不承诺更伤信任。solo 阶段一套现实的起步值：

| 严重度 | 大白话 | 首次回复 | 解决目标 |
|---|---|---|---|
| **紧急**（用了就崩 / 付了钱用不了 / 数据像是丢了） | 用户被彻底挡住 | **当天内**（醒着的话几小时内） | 24h 内给方案或明确进展 |
| **一般**（某功能不好用 / 有疑问 / 小 bug） | 能绕开，但难受 | **1 个工作日内** | 1 周内 |
| **建议 / 想要新功能** | 不是坏，是想要更好 | **2 个工作日内**给一句"收到，记下了" | 进需求池排期，不承诺时间 |

> 关键不是数字多漂亮，是**你能稳定做到**。先承诺保守值，做顺了再收紧。一条铁律：**哪怕还没解决，也要先回一句"收到，在看了"**——把用户从"没人理"的焦虑里捞出来，比真修好还重要。

---

## 三、谁处理（solo = 你，但要有"分诊"动作）

只有你一个人，但仍要有「分诊」这一步——花 30 秒给每条工单**贴个标 + 定优先级**，避免被一堆小事淹没、把真紧急的拖了。

收到一条 → 30 秒分诊：

1. **判严重度**（紧急 / 一般 / 建议，见上表）→ 紧急的插队先处理。
2. **判类型**：是 bug？是用法问题（FAQ 能答）？是新功能请求？
   - **用法问题** → 直接答 + 看要不要进 FAQ。
   - **bug** → 自己复现，按事故响应判级，走修复流程（见 [`../run/incident-response.md`](../run/incident-response.md)）。
   - **新功能请求** → 不在工单里现答"做不做"，丢进反馈闭环排期（见 [`./feedback-loop.md`](./feedback-loop.md)）。
3. **记一行**：谁、什么问题、结论 / 当前状态。

---

## 四、什么情况升级（solo 的"升级"= 拉高你自己的优先级）

没有二线团队，但仍要明确"哪些信号一出现，就该放下手头别的事、当成事故处理"：

- **多个用户同时报同一个问题** → 大概率线上故障，不是个例 → 立刻按事故走（[`../run/incident-response.md`](../run/incident-response.md)）。
- **涉及数据安全 / 疑似数据泄漏 / 跨账号看到别人数据** → **最高优先级**，立刻停下查（这是产品红线）。
- **付费 / 账单相关**（扣错钱、付了没开通） → 当天必处理，钱的事最伤信任（见 [`./billing-subscription-ops.md`](./billing-subscription-ops.md)）。
- **用户要求删除 / 导出他的数据**（合规请求） → 走合规流程，有法定时限，不能拖（见 [`./compliance-and-privacy.md`](./compliance-and-privacy.md)）。
- **同一个问题你已经回过 3 次还在出** → 不是答得不够清，是产品/文档有结构性缺陷 → 停下从根上改。

---

## 五、常见问题沉淀成 FAQ（让重复问题自己消失）

**同一个问题被问第 2 次，就该写进 FAQ。** 每答完一条值得复用的，顺手沉淀，越攒越省事。

- **放哪**：一个用户能自己搜到的地方（帮助中心 / 产品内 FAQ 页 / 文档站）。
- **怎么写**：用**用户的话**描述问题（不是你的内部术语），答案分步、能照着做。
- **定期回看**：每月扫一遍支持记录，**被问最多的前 5 个问题**——要么写进 FAQ，要么干脆改产品让这个问题不再发生（最好的支持是"根本不用支持"）。

> FAQ 是反馈闭环的一种"轻量出口"：有些"问题"不值得改代码，写清楚 FAQ 就解决了。和正经需求的分流见 [`./feedback-loop.md`](./feedback-loop.md)。

## 六、工单处理 checklist（每条工单照着走）

复制这段，每条工单过一遍：

```markdown
## 工单 <编号 / 日期>
- [ ] 记录来源 + 用户 + 原始问题（用户原话）
- [ ] 分诊：严重度（紧急/一般/建议）+ 类型（用法/bug/新功能）
- [ ] 在 SLA 时限内发出**首次回复**（哪怕只是"收到，在看了"）
- [ ] 处理：
      - 用法问题 → 答 + 判断是否进 FAQ
      - bug → 复现 → 按事故响应判级 → 修复 → 回告
      - 新功能 → 丢进反馈池排期，回一句"记下了"
- [ ] 是否触发升级信号？（多人同报 / 数据安全 / 账单 / 合规 / 同问题第3次）
- [ ] 给用户**最终结论**，确认问题解决（闭环，别让它悬着）
- [ ] 值得复用 → 沉淀进 FAQ
- [ ] 是真实需求 → 接力到反馈闭环
```

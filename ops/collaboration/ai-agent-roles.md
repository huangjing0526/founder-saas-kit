# AI / Agent 分工

> 一个人带着 AI 做产品，最该想清楚的第一件事是：**谁干什么、谁来把关、什么时候轮到人**。
> 这份文档把「主 agent / 子 agent / 只读审查 agent / 人（founder）」四类角色的边界画清楚，
> 让协作不靠口头默契，而靠一份能查的分工表。

---

## 1. 四类角色

| 角色 | 是谁 | 干什么 | 不干什么 |
|------|------|--------|----------|
| **主 agent** | 你日常对话的那个 AI | 接需求、拆任务、写代码、跑测试、按需派子 agent、整合结果 | 不私自拍方案确认、不私自宣布「交付」 |
| **子 agent** | 主 agent 派出去的专项执行体 | 一段相对独立、可并行的子任务（实现某页面 / 补一批测试 / 做一次调研） | 不跨出被派的范围、不自行扩需求 |
| **只读审查 agent**（reviewer） | 三个故意「不给写工具」的审查员 | 在主 agent 宣称完成 / 刚改完某类代码后，**只指出问题 + 给建议**，附 `文件:行号` 证据 | 绝不改代码——裁判不下场踢球 |
| **人（founder）** | 你 | **方案确认**（开工前拍板）+ **验收**（交付前点头） | 不必逐行盯实现、不必逐次确认子任务 |

核心原则：**实现与审查分离，方案与验收归人。**

---

## 2. 主 agent 干什么

主 agent 是协作的中枢，负责：

- **接需求、判规模**：小改动（bug / 样式 / 字段）直接做；新页面 / 架构变更 / 中大任务先出方案等人确认，不直接写代码。
- **拆任务**：把大任务拆成可独立交付的子任务，每个子任务边界清晰（建议子任务文件数 ≤3 小 / ≤5 中大）。
- **实现 + 自测**：写代码、跑测试、跑机检 lint。
- **决定何时派子 agent**（见 §3）。
- **整合 + 自检**：把子 agent 的产出合回主线，输出前过一遍自检清单。
- **交付前先过审查**：在向人宣布「做完了」之前，主动触发对应 reviewer（见 §4）。

主 agent **不**做的：替人拍板方案、替人验收、私自扩出需求之外的业务规则。

---

## 3. 什么时候派子 agent

派子 agent 的判断标准是「**这段工作能不能相对独立地交出去、并行做、最后整合**」：

| 适合派子 agent | 不适合派子 agent |
|----------------|------------------|
| 一段独立的探索 / 调研（搜代码库、查某个机制怎么实现） | 需要和主线频繁来回、强耦合的微调 |
| 可并行的实现（设计阶段同时出交互稿 + 视觉稿 + 架构审计） | 一两行的小修小补（主 agent 直接做更快） |
| 一批同质重复工作（给若干页面补测试） | 需要人实时拍板的方案决策 |
| 一段长链路里的某一阶段（按阶段接力，见 [unattended-handoff.md](./unattended-handoff.md)） | — |

一句请求里可以让主 agent **并行派多个子 agent**（如「同时让产品稿 agent 和架构审计 agent 处理这份方案」）。

> 子 agent 拿不到主对话的完整上下文，只能看到被派下来的指令——所以派活时要把背景、目标、产出路径写清楚，并要求子 agent 在最终消息里直接返回结论（而不是写进文件让人去找）。

---

## 4. 只读审查 agent（三个 reviewer）

这是协作里**最该建、最容易被省掉**的一环。AI 最大的风险不是写错代码，而是「**好心办坏事**」——自作主张加规则、悄悄漏掉隔离、零验证就说做完。三个只读审查员各盯一条「最容易出事、又最难靠机检覆盖」的红线：

| Reviewer | 盯哪条红线 | 什么信号触发它 |
|----------|-----------|----------------|
| [`business-rule-reviewer`](../../engineering/enforcement/subagents/business-rule-reviewer.md) | 有没有私自新增**需求之外**的业务逻辑（额外校验 / 自动副作用 / 状态流转约束 / 硬编码业务常量 / 编号生成 / 数据格式归一化），有没有登记进业务规则登记表 | 主 agent 刚加了 if 校验 / 默认值 / 自动触发逻辑 / 硬编码阈值 |
| [`tenant-isolation-reviewer`](../../engineering/enforcement/subagents/tenant-isolation-reviewer.md) | 新增 / 改动的数据库查询是否真做到**跨租户隔离**（租户过滤、软删除过滤、列表与统计共用同一 where、共享池 OR 条件、数据范围权限、返回体不泄漏他租户数据） | 主 agent 刚写完 / 改完 service / route 下的数据库查询 |
| [`delivery-verification-reviewer`](../../engineering/enforcement/subagents/delivery-verification-reviewer.md) | 在主 agent 宣布「做完了」之前，核查有没有**能证明功能正确的新鲜证据**——而不是拿「lint 过了 / 应该没问题 / 改完了」当完成证据 | 主 agent 说「功能已完成 / 已修复 / 可以交付」 |

### 它们共用一套范式

四点共性（完整方法论见 [`REVIEWER-PATTERN.md`](../../engineering/enforcement/subagents/REVIEWER-PATTERN.md)）：

1. **只读**：`tools: Read, Grep, Glob`，故意不给写工具——审查员一旦能改代码就会「顺手修了」，审查和实现混成一团，没人再独立把关。修复必须交回主 agent。
2. **凡断言必附证据**：每条结论都带 `文件:行号` 或一条可复跑的验证命令。「我觉得这里没问题」不算结论。
3. **BLOCK / WARN / PASS 三级**：给「不确定」留一个诚实的档位——逼审查员在「过 / 不过」之间二选一，它要么误报要么漏报。
4. **负向确认**：输出结尾必须有一段「我查了 X / Y / Z，这几项都 ✓」的清单，把沉默变成有据可查的覆盖面。

> **要不要造第 4 个 reviewer？** 把你项目里「出事 = 大事故、又测不出」的那条红线（如「钱算错」）照这套范式造一个。判断标准：**如果靠 grep / lint 就能 100% 覆盖，写成机检脚本，别造 reviewer**——reviewer 的价值恰恰在「脚本测不出的语义判断」。详见 `REVIEWER-PATTERN.md`。

## 5. 人（founder）干什么

人只管两件事，但这两件是**不可外包**的：

1. **方案确认**（开工前）：新页面 / 架构变更 / 中大任务，AI 先出方案，人拍板了才开工。方案对齐后 AI **连续执行不逐步打断**——人不必逐个子任务点头。
2. **验收**（交付前）：AI 交付时给一份**大白话上线说明**（改了什么 / 影响哪些用户 / 出问题最可能在哪），人据此验收。

**中途需要人介入的唯一情形**：破坏性操作（删表 / 删数据 / 删字段）、执行报错、发现原方案覆盖不到的新决策点。除此之外 AI 自行推进。

> 之所以人只抓「方案 + 验收」两头：中间的实现细节有主 agent 推进、有三个 reviewer 把关，人盯每一行既盯不过来、价值也低。人的稀缺注意力该花在「方向对不对」和「能不能验收」上。

---

## 6. 一次典型协作的角色流转

```
人：给方案 → 拍板
        ↓
主 agent：拆任务 → 实现 →（按需）派子 agent 并行做某些段
        ↓
主 agent：刚改完数据库查询 → 触发 tenant-isolation-reviewer
主 agent：刚加了业务校验   → 触发 business-rule-reviewer
        ↓（reviewer 给 BLOCK/WARN/PASS + 证据，主 agent 据此修）
主 agent：准备说「做完了」 → 先触发 delivery-verification-reviewer
        ↓（拿到新鲜验证证据）
主 agent：给大白话上线说明
        ↓
人：验收 → 点头
```

跨会话 / 隔夜接力时，把「当前在第几步、下一步谁来做」写进 Handoff —— 见 [unattended-handoff.md](./unattended-handoff.md)。
新会话 / 新人 / 新 AI 怎么快速进入状态 —— 见 [onboarding.md](./onboarding.md)。

---

## 一句话记住

> 主 agent 推进、子 agent 并行分担、三个只读裁判分别盯死最难机检的红线、人只抓方案与验收两头——
> 把「谁干什么、谁把关、什么时候轮到人」写成一份能查的分工，而不是靠默契。

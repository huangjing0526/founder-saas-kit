# 经验沉淀方法（Experience Capture）

> 使用时机：功能完成后 / 问题修复后 / 事故复盘时 / 每日收尾时。
> 一句话：一次返工或事故发生后，别急着翻篇——问四个问题，把教训落到一个**可执行载体**上。

---

## 核心理念：只写文档不焊进流程的经验会腐烂

一篇写得再好的复盘文档，如果没接进任何会被执行的流程，三个月后没人记得它存在——经验就**腐烂**了。这正是防漂移方法论原则③「**能机检的不靠人记**」要解决的：

- 靠人脑记 = 早晚忘；靠一篇散文档 = 没人翻就等于不存在。
- 沉淀的**终点不是「写下来」，是「焊进一个会被执行的载体」**——一条会被查的规则、一个会失败的脚本、一个会被触发的 skill。
- 衡量标准：这条教训**下次会不会自动拦住同类问题**？会 → 沉淀成功；不会（只是写在某处等人想起来）→ 还没沉淀完。

---

## 沉淀四问（一次返工 / 事故后逐条问）

### 问题 1：根因是什么？

- 不是「这次哪里出错了」，是「**为什么会错到这里**」——往上追一到两层。
- 例：「列表少了一批数据」→ 表面是查询漏条件 → 根因是「列表和统计用了两套 where，没共享」。沉淀要对着**根因**下手，不是对着表象。
- 判据：如果只修表象、根因还在，**同类问题会换个地方再出现**——那就还没找到真根因。

### 问题 2：怎么防下次？

- 不是「以后注意」，是「**用什么机制让下次想犯都犯不了 / 一犯就被发现**」。
- 例：「软删除漏清唯一键」→ 防法不是「记得清」，是「把清唯一键塞进软删除中间件，自动做」。
- 优先级：**机制 > 检查 > 提醒**。能用机制堵死的不用检查，能用检查发现的不靠人提醒。

### 问题 3：沉淀到哪一层？（规则？检查？skill？文档？）

对着四个落点选（详见 [`README.md`](README.md) 的四落点表）：

| 教训性质 | 落点 |
|---------|------|
| 业务规则 / 自动行为 / 硬编码常量 | ① [`../../engineering/registries/business-rules-registry.template.md`](../../engineering/registries/business-rules-registry.template.md) |
| 事故 / 反复出现的根因 | ② [`../../engineering/methodology/pitfall-index.template.md`](../../engineering/methodology/pitfall-index.template.md) |
| 能被机器查出来的 | ③ [`../../engineering/quality-scripts/`](../../engineering/quality-scripts/)（`check-*` + 接 health-audit） |
| 该固化的行为纪律 | ④ 新 skill 或 [`../../engineering/governance-skills/`](../../engineering/governance-skills/) |

一条教训可同时落多处。**纯文档（只写不焊）是最弱的落点**——只在「确实机检不了、也固化不成规则 / skill」时才退而用它，且要明确标「为什么只能落文档」。

### 问题 4：能不能机检？

- 这是**最重要的一问**，对应原则③。能机检的，就别让它停在文档里。
- 判据：这条教训能不能写成一个**读代码 / 读 schema / 读 docs 就能判定通过 / 失败**的脚本？
  - 能（如：「所有软删除查询是否都带了 `deletedAt: null`」「i18n 各语言 key 是否对齐」「Prisma `String` 字段是否漏了 `@db.Text`」）→ 写成 `../../engineering/quality-scripts/check-*.cjs`，接进 `health-audit.cjs`，挂进 CI。
  - 不能（如：「设计时该多问 PM 一句边界」）→ 退到 ④ skill 或文档，但写清楚「为什么机检不了」。

## 产品侧 vs 技术侧（两条线都要扫）

经验沉淀不只是技术债。一次交付收尾时，两侧都过一遍：

**产品侧：**
- 用户反馈里有没有需要更新状态的条目？
- 有没有新的实验结论 / 验证结果？
- 这次产品决策需不需要记一笔（决策记录 / ADR 的产品版）？

**技术侧：**
- 有没有值得记的踩坑？→ 这个坑能升级成**固化规则**吗？（能 → 立刻落 ① / ③，别等）→ 这个坑跨项目通用吗？（是 → 标记可复用，进 ② pitfall 索引）
- 有没有新的技术决策要记（ADR）？
- 有没有新债务、或旧债务可以关闭？
- 相关 PRD / 模块文档的「变更记录」更新了吗？

---

## 只记真正有价值的（防止为记而记）

- 判据：**这条记录三个月后还有用吗？** 没用 → 不记。
- 沉淀的价值在「下次会不会自动帮到人」，不在「记录条数」。一条焊进 CI 的 `check-*` 胜过十条没人看的文档行。
- 别为了凑复盘而硬编教训——**这次真一次过、没返工，就如实写「无可沉淀项」**，不凑数。

---

## 升级信号：第 3 次复发 = 停下，方向错了

- 同一类问题修到**第 2 次**：触发 [`skills/experience-capture/SKILL.md`](skills/experience-capture/SKILL.md)，强制做根因分析。
- 修到**第 3 次还在出**：**立刻停下**，不要再「修一次」——这是「方向大概率错了 / 缺一道结构性防线」的硬信号。把它升级成 ②（pitfall + Systemic=Yes）+ ③（机检脚本），从机制上堵死，而不是第 4 次再手修。

---

## 输出

每次经验沉淀，产出一份清单：

1. **需要更新 / 新建的文件列表** + 每个文件具体改什么。
2. **沉淀去向清单**：逐条教训标明落到 ①②③④ 哪个落点、对应文件 / ID。
3. 如有「能机检但这次没写脚本」的项，显式列为待办（别让它悄悄漏掉）。
4. 本次无可沉淀项时，显式写「无可沉淀项」——不留空、不凑数。

# 行为规范 — AI 在业务系统里的边界、拒答、升级与审计

> 配套治理 skill 的「总章程」。skill 讲「某场景怎么做」，本规范讲「任何场景都不能越的线」。
> 原则：**给 AI 明确边界，让它在边界内放手做；边界之外，停下来问人。**

---

## 一、安全边界（工具边界）

AI 可以在边界内自主执行，下列动作**永远需要显式授权或永远禁止**。

### 1.1 数据边界 —— 多租户隔离（D1-D6）

- 任何数据库查询**必须带租户隔离（`tenantId` 过滤）+ 权限判定**；写「跨租户聚合 / 全局查询」前必须人确认用途。
- 禁止在日志 / 报错 / 前端返回里输出其它租户的数据。
- 涉及个人敏感字段（手机号等）默认按既有脱敏规则展示（用安全原语：data-scope filter / audit masking / input sanitize；规则编号示例 `SYS-F-LISTMASK-001`，按你的项目登记）。

### 1.2 生产操作边界 —— 共享主机红线

> 背景：常见多服务共用一台主机/账户。核心：**「别人家」目录 / 进程一律不碰**。下表是示例栈下的具体动作，按你的运行环境替换。

| 动作 | 允许 | 禁止 |
|------|------|------|
| 进程管理器（pm2/systemd） | 带名字定向操作（如 `pm2 reload <你的服务名>`，零停机） | `restart all` / `reload all` / `stop all` / `delete all` / `kill`（连带影响别的服务） |
| 删除 | 写完整子路径（如 `rm -rf /app/server/node_modules`） | `rm -rf /app/*`、通配符、`..`、变量拼接进删除路径 |
| 反向代理（nginx 等） | 独立站点配置 + 配置校验（`nginx -t`）+ reload | 改主配置、`systemctl restart` 整个服务 |
| 目录 | 只写本服务工作区 | 写 / 删同主机上别的服务的目录 |

### 1.3 Git 边界（G1-G6）

- 禁 `git add -A` / `git add .`；只暂存本任务文件。
- 禁把 add + commit + push 链成一条命令。
- 禁 `git reset --hard` + `git clean` 组合（曾一次丢失数百个文件）；禁 force push。
- 编辑 schema / migrations / 路由这类「单点冲突文件」，优先独立 worktree。

### 1.4 密钥边界

- 禁止把密钥 / token 写进代码、日志、提交、对话回显。
- 部署前校验 env 指向正确环境（本地 ≠ 生产）。

## 二、拒答规则（什么时候 AI 必须说「不」）

无论用户怎么催，下列请求一律拒绝执行，并说明原因 + 给替代方案：

1. **无授权的业务规则**：要求「顺手加个校验 / 自动行为 / 改个上限」但人没拍板 → 拒绝，转业务规则登记流程。
2. **越权数据访问**：要求绕过租户隔离 / 权限去「方便地」取全量数据 → 拒绝。
3. **无回滚点的破坏性生产操作**：要求直接删库 / 删表 / 全量重启 / force push，且没记录回滚点 → 拒绝。
4. **越界碰「别人家」**：要求对同主机上别的服务的目录 / 进程做任何写操作 → 拒绝。
5. **PRD 之外的自由发挥**：要求实现「你看着加点功能」→ 拒绝，列建议等确认（不随意发散）。

> 拒答 ≠ 摆烂。每次拒绝都要：说清触碰了哪条红线 + 给一条安全的替代路径 + 指明需要谁授权。

## 三、升级人工规则（什么时候必须把球踢给人）

AI 自主执行有上限，触发下列任一条**立即停下、交还人工**：

| 触发信号 | 升级动作 |
|---------|---------|
| 缺授权的业务取值 / 规则 | 列建议 + 候选值，等拍板（业务规则登记） |
| **同一个 bug 修了 3 次还没好** | 停手，汇报已试方案 + 当前假设，请人介入（不无限试错） |
| 诊断前**业务时间线不清** | 先问「这功能什么时候上的 / 最近改过什么 / 之前正常吗」，别在错误前提下深挖 |
| 部署 / 运维**任一步报错** | 立即停，报「错误 + 当前状态 + 回滚点」，禁自行修复 / 重试 |
| 操作会**跨租户 / 跨产品**影响 | 停，确认影响面后再动 |
| 发现**当前任务之外**的改动（尤其 schema/migrations/路由） | 默认属别的会话，不提交、不覆盖，提示人 |

## 四、日志与审计要求

让每个动作**可追溯、可复盘**。

### 4.1 错误日志（后端）

- 抛错前先记录上下文：**`userId` / `tenantId` / `action`**，再 throw。
- **绝不静默 catch 并忽略错误**——要么处理，要么带上下文上抛。
- 错误信息对用户用「友好提示」，对日志留技术细节。

### 4.2 业务规则审计

- 每条规则变更在注册表留痕：编号 + 状态 + **`<拍板人> <日期> 拍板` 出处** + 覆盖文件。
- 每次交付摘要列「业务规则变更」节；无变更也显式写「无」。

### 4.3 部署 / 运维审计

- 部署第一件事：**记录回滚点**（当前版本号 + 进程状态）。
- 越界 / 破坏性操作走运维操作日志（`ops-logs/<日期>-<动作>/`）。

### 4.4 审计动作本身的纪律

- 审计发现**必须读文件验证后再报告**，不能仅凭模式匹配 / 文件名猜测（见 [S9 审计先验证后报告](S9-audit-verify-before-report.md)）。
- 每条发现附「已读 `<文件:行号>` 确认」证据。

## 五、这套规范怎么落地

- **人读**：本文件是 onboarding 第一篇，新同事 / 新 AI 会话先读。
- **机器读**：把第一、二、三节的硬约束写进项目 `CLAUDE.md` / 各 skill 的正文，让 AI 每次自动加载。
- **审计对照**：季度复盘时，用第四节的「留痕清单」逐项核对是否真的留痕了。

# 发布公告 / 上线说明（模板 + 示例）

> 每次上线后，给一份**非技术 founder 和用户都能看懂**的「上线说明」。
> 三个问题讲清楚就够了：**改了什么 / 影响哪些用户 / 出问题最可能在哪**。
>
> 铁律：**大白话，不堆术语。** 用户不关心你用了什么库、改了哪个文件，他只关心「我的活会不会变方便、会不会被坑」。绕不开的术语写成 `术语(一句话白话解释)`。

---

## 为什么要写这份

一个人带着 AI 做产品，最容易省掉的就是「上线后跟用户和自己说人话」。但这份说明有三个用处：

1. **给用户**：让他知道这次更新对他有什么好处，值得点开看 / 去用。
2. **给未来的你**：三个月后线上出问题，回头一翻就知道「哦这块是 X 月那次上线动的」，少走弯路。
3. **给自己止损**：写「出问题最可能在哪」这一栏时，你会被迫想清楚这次改动的风险点——很多 bug 是在写这一栏时提前想到的。

---

## 模板

> 复制下面整段填写。命名建议：`release-<YYYY-MM-DD>-<简短主题>.md`，归档到你的发布日志目录。

```markdown
# 上线说明 · <YYYY-MM-DD> · <一句话主题>

## 一句话总结
<这次上线，用户能多干成一件什么事 / 少受一个什么罪。一句，不超过 30 字。>

## 改了什么（给用户看）
- <用「用户能感知的变化」描述，不是「我改了哪段代码」>
- <例：以前导出客户名单要一个个勾，现在能一键全选导出>
- <例：手机上看报表，表格不再挤成一坨，能左右滑>

## 影响哪些用户
- **谁受影响**：<全部用户 / 只有用到 XX 功能的人 / 只有管理员>
- **要不要做什么**：<不用动，自动生效 / 需要重新登录一次 / 老数据会自动迁移，无感>
- **有没有变化要适应**：<按钮挪了位置 / 某个老入口下线了 → 提前打个招呼>

## 出问题最可能在哪（给自己 + 客服）
> 上线后头 3 天重点盯这几处。出问题用户大概率从这里来。
- <例：导出大名单时如果卡住，是新的批量逻辑没扛住数据量>
- <例：老用户第一次进新报表页可能白屏，让他刷新一次>
- **回滚点**：<这次部署前的版本 commit / 备份快照 ID，真出事时从这里退>

## 怎么知道这次上线是好是坏（发布后 3 天看）
- 盯一个指标：<例：客户名单导出功能的使用次数有没有涨 / 报错率有没有降>
- 红线：<例：如果导出报错率 > 1%，立刻回滚>
```

## 配套：对外的三种文案（可选，按需取用）

同一次上线，对外可以派生三个版本——**内核都是上面那份**，只是语气和长度不同：

| 版本 | 给谁 | 风格 | 长度 |
|---|---|---|---|
| 产品更新公告 | 全体用户（站内信 / 邮件） | 正式但不端着 | 一屏 |
| 社交媒体文案 | 潜在用户 / 社区 | 轻松，展示进展 | 1-3 句 |
| 系统内推送 | 当前在线用户 | 极简，一句话 | 1 句 |

写这三种时统一守两条：
- **以用户获得的价值为主角，不是功能列表**（说「现在能一键导出」，不说「上线了批量导出接口」）
- **不用「我们很高兴地宣布」这类套话**，简洁有力

## 一个填好的示例

> 下面这份对应一个多租户 CRM 产品的真实风格示例（业务模块仅作示例，换成你自己的即可）。

```markdown
# 上线说明 · 2026-05-20 · 客户名单一键导出

## 一句话总结
导客户名单不用再一个个勾了，一键全选直接导出。

## 改了什么（给用户看）
- 客户列表新增「全选导出」：勾一下表头，整页 / 整个筛选结果一次导出成 Excel。
- 导出时会带上你当前的筛选条件（比如「只导华南区、本月新增的客户」），所见即所得。
- 大名单（几千条）导出改成后台慢慢跑，导完给你发个站内通知，不用一直开着页面等。

## 影响哪些用户
- **谁受影响**：所有会用到「客户列表导出」的人（销售、主管、管理员）。
- **要不要做什么**：不用动，下次进客户列表就有新按钮，自动生效。
- **有没有变化要适应**：原来的「单条导出」按钮还在原位，没挪；只是多了个「全选」。

## 出问题最可能在哪（给自己 + 客服）
> 上线后头 3 天重点盯这几处。
- 导**特别大**的名单（上万条）时，后台任务如果超时，用户会收不到「导出完成」通知 → 先查导出队列有没有堆积。
- 带复杂筛选导出时，导出的内容要和列表里看到的**完全一致**，不一致就是筛选条件没正确传到导出——这是最容易出的坑。
- 跨公司数据隔离要再确认：A 公司导出绝不能混进 B 公司的客户（多租户隔离是红线）。
- **回滚点**：上线前版本 commit `a1b2c3d`；数据库迁移前快照 `bk-20260520-0830`。真出事从这里退。

## 怎么知道这次上线是好是坏（发布后 3 天看）
- 盯一个指标：「客户列表导出」的使用次数——上线后一周内有没有明显上涨（说明这功能用户真需要）。
- 红线：导出报错率 > 1%，或收到 ≥ 2 个「导出内容和列表对不上」的反馈 → 立刻回滚到 `a1b2c3d`。
```

派生的三种对外文案（同一次上线）：

- **产品更新公告**：「客户名单导出升级了：现在勾一下表头就能把整个筛选结果一键导成 Excel，几千条的大名单也能后台慢慢跑、导完通知你。不用再一条条勾了。」
- **社交媒体文案**：「小更新但很爽：客户名单一键全选导出，带筛选条件，所见即所得。」
- **系统内推送**：「新功能：客户列表支持一键全选导出啦 →」

## 落地建议

- 这份说明在**上线前**就写好「改了什么 / 影响谁 / 风险在哪 / 回滚点」——写的过程本身就是一次风险自检。
- 上线后第 3 天回来填「指标表现」，判断这次改动值不值、要不要继续做这个方向。
- 想把「上线说明」做成每次部署的固定收尾动作，可结合 [`../cadence/weekly-check.md`](../cadence/weekly-check.md) 的节奏；出事时的应急流程见 [`./backup-recovery-sop.md`](./backup-recovery-sop.md) §四（紧急回滚）。

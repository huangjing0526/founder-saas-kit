# 只读审查 Reviewer 范式

这三个 subagent（`business-rule-reviewer` / `tenant-isolation-reviewer` /
`delivery-verification-reviewer`）不是各写各的，它们共用同一套范式。
理解了这套范式，你可以照着造你自己的**第 4 个、第 5 个 reviewer**——
把你项目里「最容易出事、又最难靠机检覆盖」的那条红线，变成一个会自己盯的审查员。

---

## 范式的五个支柱

### 1. 只读（Read / Grep / Glob，绝不 Edit/Write）

frontmatter 里 `tools: Read, Grep, Glob`——**故意不给写工具**。
- 审查员一旦能改代码，就会忍不住「顺手修了」，于是审查和实现混成一团，没人再独立把关。
- 只读 = 它只能「指出问题 + 给建议」，修复必须交回主 agent。**裁判不下场踢球。**

### 2. 附 `文件:行号` 证据（禁止凭印象）

每一条结论——无论 BLOCK 还是 PASS——都必须带 `文件:行号`，或一条**可复跑的验证命令**。
- 这是「防漂移」的核心：关于「系统有没有做 X」的任何断言，都要能被第三个人按图索骥验证。
- 「我觉得这里没问题」不算结论。「customer.service.js:42 的 where 带了 tenantId ✓」才算。

### 3. BLOCK / WARN / PASS 三级（而不是「过 / 不过」）

- **BLOCK**：确认有问题、且后果严重（数据泄漏、未授权规则、零验证就说完成）→ 必须停下修。
- **WARN**：疑似有问题，但需要更多上下文才能定性 → 标出来让人确认，不硬判。
- **PASS**：检查过、有证据、可放行。

三级的意义：**给「不确定」留一个诚实的档位**。逼审查员在 BLOCK / PASS 之间二选一，
它要么误报（侵蚀信任），要么漏报（失去价值）。WARN 让它能诚实说「这条我吃不准」。

### 4. 负向确认（没发现问题，也要说清查了什么）

输出结尾必须有一段「已检查 X / Y / Z 未发现问题」的清单。
- 「PASS，没问题」是廉价的、不可信的。**「我查了软删除、查了列表/统计一致、查了返回体不泄漏，这三项都 ✓」才可信。**
- 负向确认把「沉默」变成「有据可查的覆盖面」，也让人一眼看出审查员**漏查了**什么维度。

### 5. 触发时机：在主 agent「宣称完成」或「刚改完某类代码」后

每个 reviewer 的 frontmatter `description` 里写清两件事：
- **WHEN**：什么信号触发它（如「主 agent 刚写完 service 查询」「主 agent 说『可以交付了』」）。
- **WHEN-NOT**：什么时候**别**触发它（如「还在开发中途」「纯前端样式改动」「泛泛巡检走机检脚本」）。

WHEN-NOT 和 WHEN 一样重要——没有它，审查员会在不相干的场景乱触发，变成噪音，最后被忽略。

## 怎么照这个范式造你自己的第 4 个 reviewer

假设你项目里「钱算错 = 大事故」，想造一个 `billing-correctness-reviewer`：

1. **复制一份现有 reviewer 当骨架**（结构最接近的那个）。
2. **写 frontmatter**：
   - `name`：短横线命名。
   - `tools: Read, Grep, Glob`（**照抄，不要加写工具**）。
   - `description`：一句话职责 + WHEN（什么改动触发）+ WHEN-NOT（什么时候别触发）。
3. **写「判定标准」**：明确列出**什么算问题**（✅ 算）和**什么不算、别误报**（❌ 不算）。
   这是 reviewer 质量的命根子——标准模糊 = 满屏误报。
4. **写工作流**：Grep/Glob 定位改动 → 读真实代码逐条核对 → 每条附 `文件:行号` → 结尾负向确认。
5. **写铁律**：只审不改、不确定降级 WARN、区分三级严重度。
6. **写输出格式**：给一个三级结论 + 发现 + 负向确认的样例块，照着填。

判断标准：**如果这条红线靠 grep / lint 就能 100% 覆盖，就写成机检脚本，别造 reviewer。**
reviewer 的价值恰恰在「脚本测不出的语义判断」——要结合调用上下文、要理解需求意图的那部分。

---

## 一句话记住

> 只读的裁判，凡断言必附证据，三级而非二元，沉默也要交代查了什么，
> 只在该出手时出手——把一条难机检的红线，变成一个会自己盯的审查员。

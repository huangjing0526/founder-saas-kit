# Founder 工时分配 tally

> 每周五花 2 分钟，估一下这周大头时间花在哪。
> 目的：判断"该不该招第一个工程师 / 第二个工程师"——不是凭感觉，靠数字。
> 阈值：连续 2 周"修线上 bug + 用户排查" > 30%，启动招聘流程。

## 怎么用

每周五在下面表格追加一行。**只估比例，不要精确到分钟**——大概对就行。
4 个分桶加起来 = 100%。

```
新功能：写新页面、新接口、新表
修 bug + 排查：用户反馈、线上 error、数据修复、回归
基础设施：测试、CI、部署、文档、重构、依赖升级
讨论 + PRD：方案对齐、需求讨论、UI 评审、不写代码的会
```

## 怎么读这个表

**单周看不出问题，看 4 周滑动平均。**

| 模式 | 信号 | 怎么办 |
|---|---|---|
| 修 bug ≤ 20% | 健康，加新功能就行 | 维持现状 |
| 修 bug 20%-30% | 接近警戒，盯一下 | 不一定要招人，但要看是不是某个模块密集报错——是的话先重构那个模块 |
| 修 bug 30%-50% **连续 2 周** | 红线，开始招聘 | 启动 senior 全栈招聘（周期 2-3 个月，到岗+磨合 1-2 个月）|
| 修 bug > 50% **任意一周** | 失火 | 当周停所有新功能，集中清 bug；如果是同一类 bug 反复出 → 架构问题 |

**讨论 + PRD > 30% 任意一周**：可能在做大改动（不一定坏），也可能方向不清在反复对齐——和 AI 一起判断哪种。

**新功能 < 30% 持续 4 周**：要么遇到瓶颈，要么节奏自然慢下来。两种情况下次 review 都该聊。

## AI 怎么帮 founder 估这个数

founder 周五说"做 tally"或"做工时表"时：

1. 拉最近 7 天 git log + commit message 类型分布：
   ```bash
   git log --since="7 days ago" --pretty=format:"%h %s" | head -100
   ```
2. 按 commit prefix 估比例：
   - `feat(xxx)` → 新功能
   - `fix(xxx)` / `hotfix` → 修 bug + 排查
   - `test(xxx)` / `chore` / `refactor` / `ci` / `docs` → 基础设施
   - 没 commit 但有方案/PRD 文档变更 → 讨论 + PRD
3. 给 founder 一行建议数字（如 "新功能 50% / 修 bug 25% / 基础设施 15% / 讨论 10%"），让 founder 微调
4. 追加到上方表格

## 常见误区

- **修 bug 包不包括"我自己跑测试发现的问题"？** 不包括——那算新功能开发的一部分。只算"用户报上来的 / 线上 error / 数据出错"才算。
- **改完一个 bug 顺手做的小优化算哪个？** 算修 bug。原则是看触发原因。
- **跨周的功能怎么算？** 按当周实际花的时间，不要回填到"完成那一周"。

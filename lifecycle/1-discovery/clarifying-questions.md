# 动手前的澄清提问清单

> 三层拆解（`requirement-three-layers.md`）让你知道「他真正要什么」；
> 这份清单让你在动手前，把这个需求**落地时绕不开的细节**问清楚。
> 一条铁律先摆这：**需求不清就问，绝不靠猜往下做**。

---

## 为什么澄清在写码/写 PRD 之前

需求里没说清的细节，开发时一定会撞上。撞上时只有两条路：

1. **停下来问** —— 慢一点，但做对。
2. **自己拍脑袋猜一个** —— 快，但有一半概率猜错，返工。

Discovery 阶段的澄清，就是把第 2 条路**提前堵死**：在还没有沉没成本时把问题问完，而不是写到一半才发现需求是空的。

---

## 必问的五类问题

### 1. 边界情况（最容易漏，也最容易出事）

需求方描述的几乎都是「正常情况」，边界要你主动追问：

- **时间冲突**：「同一时间能不能有两条？冲突了怎么办——拒绝 / 覆盖 / 并存？」
- **状态前置**：「这个操作要求对象处在什么状态才能做？（例：只有草稿能编辑，已提交的能不能改？）」
- **数量上限**：「有没有上限？超了怎么办——拦截 / 警告 / 静默？」
- **空与异常**：「没有数据时显示什么？出错了给用户看什么？」
- **权限/可见性**：「谁能看、谁能改？跨人/跨组织的数据要不要隔离？」

> 这些边界一旦确定，多半会变成**业务规则**——记得交给业务规则总账登记（任何自动校验 / 自动行为 / 硬编码上限都要登记，别偷偷加）。

### 2. 谁用（Who）

- 「这是给哪类角色用的？（例：一线 / 主管 / 管理员——示例角色，按你的业务换）」
- 「是一个人的偏好，还是一类人的共性刚需？」（接 `feedback-to-requirement.md` 的噪音 vs 信号）
- 「他在什么场景下用？（办公室 / 路上 / 高频 / 偶尔）」

### 3. 成功长什么样（Definition of Done）

- 「这个功能上线后，怎么算成功？用户的哪个动作/指标会变？」
- 「你会怎么验收它？给我一个你会亲手走一遍的路径。」
- 「不解决哪件事，就算做了也白做？」（找出真正的验收核心）

> 说不清「成功长什么样」的需求，往往是没想透——退回三层拆解。

### 4. 现状与替代路径

- 「现在没有这个功能，你是怎么凑合的？」（现有替代路径 = 判优先级的关键）
- 「这件事现在有多痛？多久遇一次？」（频次 × 痛感）

### 5. 不做什么（接下方「范围裁剪」）

- 「这一版**不打算**覆盖哪些情况？」
- 「哪些是『以后再说』，不是『现在就要』？」

## 需求自相矛盾时——停下来问，绝不猜

需求方在不同地方说的话可能打架。最典型：

> A 处说「这个字段必填」，B 处又说「这个字段可选」。

这种时候，**任何一种猜测都有一半概率是错的**，而且错的那半会在上线后变成 bug。处理方式只有一种：

1. **停下来，把矛盾两处并排列出来**（原话 + 出处）。
2. **给出你看到的冲突点**，不替对方选边。
3. **等明确答复**，再往下做。

```
⚠️ 需求冲突，需要你拍板：
  - A 处（<出处>）：「<字段> 必填」
  - B 处（<出处>）：「<字段> 可选」
这两条互斥，我不替你猜。请确认到底哪个为准。
```

> 反模式：「我觉得 B 处更合理，就按可选做了。」——这不是高效，这是赌博。**违反规则的精神**：你不是在遵循需求，是在替需求方做了他没授权你做的决定。

凡是靠猜才能填的点，统一用 `[NEEDS CLARIFICATION: <问题 + 候选>]` 标出，可 `grep -rn "NEEDS CLARIFICATION"` 扫；**带未消解标记的需求不准进 PRD / 不准开写**。

## 范围裁剪（Scope Cutting）——决定「不做什么」

> **砍需求和加需求一样重要，甚至更重要。**
> 一个想清楚的需求，一半价值在于明确了它**不解决**什么。

### 为什么必须主动裁

需求像滚雪球——每问一个边界，都会冒出「那要不要也支持……」。如果全都做：

- 范围无限膨胀，永远上不了线。
- 核心价值被边角功能稀释，用户反而抓不住重点。
- 每个「顺手加的」都是没被验证的假设，是未来的维护负担。

### 怎么裁

对每一个冒出来的子需求，过一遍这把尺：

| 问 | 留 | 砍 / 推后 |
|----|----|----|
| 不做它，核心目标还成立吗？ | 不成立 → 留 | 成立 → 砍/推后 |
| 多少用户真的会撞上这个情况？ | 高频共性 → 留 | 边角个案 → 推后 |
| 它是「现在就卡死」还是「以后更好」？ | 卡死 → 留 | 锦上添花 → 推后 |

### 裁剪要留痕

裁掉的不是消失，是**显式记录「这一版决定不做 X，因为 Y」**：

```
本版范围：
  做：<核心 1>、<核心 2>
  这一版明确不做（裁剪记录）：
    - <子需求 A> —— 原因：边角个案，<5% 用户撞上，推到 v2
    - <子需求 B> —— 原因：不影响核心目标成立，锦上添花
```

留痕的好处：需求方一眼看到你**主动**砍了什么、为什么砍，他可以反对（「不行，B 必须做」），但不会出现「你怎么没做 B」的扯皮——因为是他点头裁掉的。

### 裁剪有真分歧时 → 升级 S11

如果「砍还是留」本身就是个有真分歧的取舍（几个互斥方向、不可逆选择），别一个人拍——升级走 `../../engineering/governance-skills/` 的 **S11（多视角决策）**：多视角发散 → 读真实材料验证 → 收敛成给业务方的拍板选项。**Discovery 把问题问清楚，S11 把分歧吵明白。**

---

## 澄清环节的产出

澄清 + 裁剪跑完，你手上应该有：

1. 五类问题的答复（边界 / 谁用 / 成功 / 现状 / 不做什么）。
2. 所有冲突点已拍板，无残留 `[NEEDS CLARIFICATION]`。
3. 一份**范围裁剪记录**（做什么 + 这一版明确不做什么 + 原因）。

这三样齐了，需求才算「想透了」——可以交给 `../2-prd/` 写正式 PRD。

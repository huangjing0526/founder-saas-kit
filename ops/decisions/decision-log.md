# 决策日志 / 轻量 ADR

> 解决一个具体的痛：**三个月后忘了当初为什么这么定**，于是把已经吵明白的事又重吵一遍，或者推翻了一个其实有充分理由的决策。
>
> 这是一份「轻量 ADR」（ADR = Architecture Decision Record，架构决策记录）。不追求重型流程——一条决策一段，能让未来的你 / 新人 / 新 AI 会话查到来龙去脉就够了。

---

## 为什么要记决策

1. **防失忆**——人对「当时的权衡」遗忘得极快。三个月后只记得「我们用了 X」，忘了「因为 Y 当时不支持某能力才没选 Y」。没记下来，就会在 Y 已经修好后还固守 X，或者反过来盲目推翻 X。
2. **新人 / 新 AI 能查到来龙去脉**——一个人带 AI 做产品，AI 会话是「失忆的」：每个新会话都不知道上个会话为什么这么定。把决策落成文档，新会话读一遍就接得上，不用你口头重讲一遍。
3. **推翻有据**——决策不是终身制。但推翻一个旧决策前，先看它当初为什么这么定、什么前提变了——而不是凭印象推倒重来。

---

## 什么决策值得记

**值得记**（想错了要返工、甚至上线翻车的）：

- **架构选型**——单体还是拆服务、要不要引入消息队列、数据怎么分层
- **技术栈**——选哪个框架 / 数据库 / 第三方服务，尤其是「难撤回」的那种
- **重要权衡**——为了 A 牺牲了 B（如：为上线速度牺牲了某种灵活性）
- **砍需求 / 划边界**——某个功能决定不做、或只做到某个边界，以及为什么

**不值得记**（别把日志写成流水账）：

- 改字段、调样式、修单点 bug
- 命名、目录摆放这类一眼能看出意图的小决定
- 任何「换个写法重来一遍成本极低」的事

> 判断标准和[多视角决策](./decision-brainstorm.md)一致：**撤回成本高 / 影响面大 → 记**；小改动直接做，不留痕。

---

## 一条决策的模板

每条决策填下面这张表。复制一份，改成你的内容：

| 字段 | 填什么 |
|------|--------|
| **编号** | 递增，如 `DEC-001`、`DEC-002` |
| **日期** | 决策定下来的日期 `YYYY-MM-DD` |
| **状态** | `提议` / `已定` / `已推翻`（推翻的注明被哪条决策取代） |
| **决策** | 一句话讲清最终定了什么 |
| **背景** | 当时面对什么问题、什么约束逼出了这个决策 |
| **备选方案及为何不选** | 认真考虑过的其它选项，逐个写明为什么没选——**这一栏最值钱**，它记的是「当时的前提」 |
| **后果 / 风险** | 这么定带来什么代价、埋了什么坑、未来可能在哪翻车 |
| **何时复看** | 给一个触发条件，到点回头看这条决策还成不成立（如「Y 框架发 2.0 后」「日活破 1 万后」） |

## 决策记录

> 下面是 1 条填好的示例（通用技术选型），照着这个格式往下追加。

### DEC-001 | 2026-06-06 | 已定

- **决策**：服务端选用 **Express**（成熟、生态广、团队熟）而非某新兴异步框架 X（性能更高但生态新、招人难）。
- **背景**：项目早期，主力是 1 个 founder + AI，要的是**快速上线 + 出问题能查到一堆现成答案**，而不是把每秒请求数压到极限。当前并发量级离任何框架的性能瓶颈都还很远。
- **备选方案及为何不选**：
  - **框架 X（高性能异步）**——基准测试确实更快，但①生态和中间件远不如 Express 丰富，遇到坑能搜到的答案少；②未来招第一个工程师时，熟 X 的人少、上手慢。性能优势在当前量级用不上，不值得用生态和招人成本换。
  - **自己撸一个极简 HTTP 层**——零依赖看似干净，但等于把所有路由 / 中间件 / 错误处理的轮子重造一遍，维护成本全压在自己身上。否决。
- **后果 / 风险**：绑定 Express 中间件生态；若未来真撞上性能墙（单机 QPS 持续打满），迁移成本不低。**缓解**：业务逻辑走分层（路由 → 服务 → 仓储），框架只在最外层，真要换时核心逻辑可复用。
- **何时复看**：单机请求量持续逼近瓶颈、或框架 X 生态成熟到招人不再是问题时——届时重评是否迁移。

## 这条日志和别的环节怎么接

- **上游 —— 多视角决策的结论落到这里**：用 [`./decision-brainstorm.md`](./decision-brainstorm.md)（多视角决策 workflow，对应治理方法论 S11）想透一个关键决策后，收敛简报里「拍板区」定下的东西，就**抄成这里的一条 ADR**——brainstorm 负责「想清楚」，本日志负责「记下来」。
- **下游 —— 被推翻的决策进复盘**：一条决策状态改成 `已推翻` 时，不只是改个字——背后通常是踩了坑或前提变了。把这个教训喂进复盘环节 [`../../lifecycle/9-retrospective/`](../../lifecycle/9-retrospective/)，让「为什么当初的判断没撑住」沉淀成下次不再犯的经验。
- **节奏 —— 每季扫一遍**：季度人工复核（见 [`../cadence/review-rhythm.md`](../cadence/review-rhythm.md)）时，逐条过本日志里「何时复看」到点的决策，确认还成不成立。

# 需求三层拆解法

> 用户说的需求，往往是他**想象出来的解法**，不是他**真正的问题**。
> 直接照着「他说的」做，做完会发现没解决他实际的痛。
> 三层拆解就是一把往下挖的铲子：从「他说要什么」挖到「他真正卡在哪」。

---

## 核心洞察

> **「我要一匹更快的马」——用户要的不是更快的马，是更快到达目的地。**

用户开口提的，是经过他自己一轮加工后的**解法**。这层加工里藏着三个风险：

1. 他的解法可能**不是最优的**（他只知道现有工具能做什么）。
2. 他的解法可能**根本不对症**（误判了自己的问题）。
3. 不同用户提同一个解法，背后**真实问题可能完全不同**。

所以拿到需求别急着出方案，先往下挖三层。

---

## 三层模型

```
┌─────────────────────────────────────────────────┐
│ 第 1 层 · 表层诉求（他说的）                      │
│   用户原话、他想象的解法、具体到某个功能/按钮     │
│   「能不能加个导出 Excel 的功能」                 │
└──────────────────┬──────────────────────────────┘
                   │  问：「你拿这个去做什么？」
                   ▼
┌─────────────────────────────────────────────────┐
│ 第 2 层 · 真实目标（他想达成的）                  │
│   去掉解法后，他真正想完成的那件事                │
│   「我要每周给老板交一份业绩汇总」                │
└──────────────────┬──────────────────────────────┘
                   │  问：「为什么这件事对你重要？不做会怎样？」
                   ▼
┌─────────────────────────────────────────────────┐
│ 第 3 层 · 根本动机（他为什么在乎）                │
│   驱动这一切的底层诉求、KPI、恐惧、约束           │
│   「老板用这份汇总判断我团队这周干得行不行」      │
└─────────────────────────────────────────────────┘
```

挖到第 3 层，你常会发现：导出 Excel 只是手段之一，真正该做的也许是一个**自动生成的周报视图**——用户压根不用手动导、手动算。

---

## 每一层怎么挖（提问法）

### 第 1 层 → 第 2 层：用「拿来做什么」剥掉解法

把用户的解法当成一个**黑盒输出**，问它服务于什么目标：

- 「你拿这个 X 去做什么？」
- 「有了 X 之后，你的下一步动作是什么？」
- 「现在没有 X，你是怎么凑合的？」（现有替代路径暴露真实目标）
- 「如果我给你一个完全不一样的方式达到同样效果，你介意吗？」（试探解法是不是硬约束）

> 关键判别：如果用户对「换个解法」很抗拒，说明这个解法本身可能是真需求（如合规要求必须是 Excel）；如果他无所谓、只要结果，说明你挖对了——第 1 层只是他的猜测。

### 第 2 层 → 第 3 层：用「为什么重要」挖到动机

- 「为什么这件事对你重要？」
- 「这件事做不成，最坏会发生什么？」
- 「谁会因为这件事来找你？」（暴露背后真正的甲方/KPI）
- 「这是你一个人的需求，还是一类人的需求？」（个案 vs 共性，接 `feedback-to-requirement.md`）

### 配套两问（判优先级，别只挖不估）

- **哪类用户有这个需求、占比大吗？**（一个边角用户的偏好 ≠ 共性刚需）
- **不做会怎样、有没有现成替代路径？**（已有替代 = 优先级可降；完全卡死 = 优先级高）

## 正反例

### 例 1：导出功能

| 层 | 内容 |
|----|------|
| ❌ **只听表层就做** | 用户说「加个导出 Excel」→ 直接做导出按钮 → 上线后用户还是每周手动算汇总，没省事 |
| ✅ **挖到真实目标** | 问「导出去做什么」→「每周给老板交业绩汇总」 |
| ✅ **挖到根本动机** | 问「为什么重要」→「老板靠这个判断团队这周的表现」 |
| ✅ **对症方案** | 真正该做的是**自动周报视图**（甚至自动推送），导出只是兜底。用户从「每周手动 1 小时」变成「打开就看」 |

### 例 2：客户跟进（示例，按你的业务换）

| 层 | 内容 |
|----|------|
| 表层诉求 | 「给客户加个『重要』标星」 |
| 真实目标 | 「重要客户别被淹没在长列表里，要能优先跟进」 |
| 根本动机 | 「漏跟一个大客户 = 丢单 = 我的业绩没了」 |
| 对症方案 | 不只是标星，而是「**待跟进**优先级排序 + 超时提醒」——直接解决「怕漏跟」这个根本恐惧，标星只是其中一种触发方式 |

> 注：lead / customer / 跟进 等都是**示例业务模块，按你自己的业务换**。

### 反例：挖过头也是错

三层拆解不是无限追问哲学。判停的信号：

- 已经能用一句话说清「他真正卡在哪」，且这句话**可被一个功能直接命中** → 停，别再追问动机的动机。
- 用户开始不耐烦、重复同样的话 → 你已经挖到底了，再问是骚扰。

> 原则：**挖到「能据此设计出对症方案」就够了**，不是挖到用户的人生理想。

---

## 输出格式

拆解完，落成一段结论交给澄清环节（`clarifying-questions.md`）：

```
表层诉求：<用户原话/想象的解法>
真实目标：<去掉解法后他真正想达成的事>
根本动机：<驱动这一切的底层诉求/KPI/恐惧>
需求人群：<哪类用户 / 占比大不大>
不做的代价：<不做会怎样 / 有无现成替代路径>
初判方向：<对症方案的雏形，不是最终设计>
[NEEDS CLARIFICATION: <挖的过程中冒出来、需求方没说清的点>]
```

> 凡是靠猜才能填的点，用 `[NEEDS CLARIFICATION: <问题 + 候选>]` 标出来，别假设着往下写——交给澄清环节问清。

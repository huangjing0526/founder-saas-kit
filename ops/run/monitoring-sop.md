# 可用性拨测与告警 SOP

> ⚠️ **这是内部 SLO（你自己拨测、自己发现挂没挂），不等于能写进合同的对客 SLA（对客户的可用性承诺）。** 监控测到的可用性是"你内部看到的稳定度"，**别直接把这个数字当成对客承诺**——对客 SLA 怎么定、为什么要留余量，见 [`../business/sla-and-status-page.md`](../business/sla-and-status-page.md)。
>
> 用途：补进程管理器（pm2 / systemd）崩溃告警的盲区 —— **进程没崩但功能挂了**（DB 连接池打满 / 外部 API hang / 内存泄漏导致响应慢但还活着）。
>
> 工具：用一个外部黑盒拨测服务（云厂商自带的「站点监控 / CMS」、或独立的 uptime 服务），定期从外部打你的健康端点。
>
> 告警通道（统一记作 `NOTIFY_WEBHOOK_URL`）：Slack / 飞书 / 自定义 webhook，任选一个能直推你个人手机的。
>
> 依赖：后端有 `/api/health`（浅检查）和 `/api/health/deep`（深检查，会真连一次 DB）两个端点。

> ⚠️ **这两个端点不是现成的，是前置工程任务——本 SOP 假设你已经实现了它们**。没有就先让 AI 加上（约半小时的活），否则下面的拨测无从打起。两个端点该返回什么：
> - **`/api/health`（浅检查）**：只证明「进程还活着、能接 HTTP」。不碰任何外部依赖，永远尽快返回 `200` + `{"status":"ok"}`。进程一崩它就连不上。
> - **`/api/health/deep`（深检查）**：在浅检查基础上**真去 ping 一次关键依赖**（数据库必查，必要时加缓存 / 关键外部 API），全通才返回 `200` + `{"status":"ok"}`；任一依赖不可达 / 超时则返回 `503` + 哪个依赖挂了。给依赖 ping 设个短超时（如 2s），别让健康检查自己 hang 住。这样「进程活着但 DB 连不上」这种"假活"才抓得到。

---

## 一、为什么要外部拨测

进程管理器只知道「进程在不在」，它看不到「进程活着但功能挂了」。外部黑盒拨测从用户视角打你的真实域名，能抓到这类「假活」：

| 选型维度 | 怎么权衡 |
|---|---|
| 拨测节点位置 | 选**离你真实用户近**的节点。用户在哪，就从哪打——跨境拨测延迟波动大、假阳性多 |
| 与基础设施同账号 | 拨测服务和你的云服务器同账号时，故障能直接关联服务器状态，排查快 |
| 价格与拨测粒度 | 多数云厂商自带的站点监控免费档**粒度为 5min**，没必要先上付费 SaaS。但**粒度直接决定告警时延**（见下一行）：要 ≤6min 告警必须有 1min 粒度；只有 5min 粒度的免费档，告警时延相应放宽到 ~10min（5min × 2 周期 + 处理延迟），或升级到支持 1min 的档 |
| 告警渠道 | 必须能对接你的 `NOTIFY_WEBHOOK_URL`（原生支持 webhook 的优先） |

**结论：solo 阶段优先用「和你云服务器同账号」的自带拨测，省一次集成、故障时能直接看到服务器。**

## 二、核心配置（首次设置，一次性 15 分钟）

### Step 1 — 进入拨测/站点监控
你云厂商控制台 → 监控（Cloud Monitor / CMS 等价物）→ 站点监控 → 新建监控。

### Step 2 — 创建主监控任务（深检查）

| 字段 | 值 | 说明 |
|---|---|---|
| 任务名称 | `<app>-prod-deep-health` | 显式标记环境与端点 |
| 监控类型 | HTTP(S) | 不是 Ping，要发真实 HTTP 请求 |
| 监控地址 | `https://<your-domain>/api/health/deep` | 用真实生产域名，不要直接打服务器 IP（反代/防火墙路径要一起测） |
| 监控频率 | 1 分钟（若免费档只有 5min 粒度则填 5min） | **这一项决定告警时延**：填 1min → 下方 Step 3 报警规则"连续 2 周期失败"≈ ≤6min 告警；只有 5min 粒度 → 同样规则下告警时延放宽到 ~10min。想要 ≤6min 告警就必须有 1min 粒度的档（见 §一选型表「价格与拨测粒度」） |
| 探测点 | 选 3-5 个离你用户近的城市 | 多点覆盖，单点故障不会误报 |
| 期望 HTTP 状态码 | `200` | `/health/deep` 在 DB 连不上时返回 503，监控立即发现 |
| 匹配响应内容 | `"status":"ok"` | 即使 200 OK，也断言 JSON 内容含 status:ok（防反代缓存的过时 200） |
| 超时时间 | 5 秒 | `/health/deep` 内部 DB ping 超时 2s，HTTP 总耗时 ≤ 5s 是正常水位 |

### Step 3 — 创建报警规则

| 字段 | 值 |
|---|---|
| 规则名称 | `<app>-prod-down` |
| 触发条件 | 探测失败次数 ≥ 2，连续 2 个监控周期 |
| 报警渠道 | `NOTIFY_WEBHOOK_URL`（Slack / 飞书 / 自定义 webhook） |
| 告警等级 | Critical |
| 静默期 | 5 分钟（避免反复刷屏，但故障持续会重新告警） |

> **关键设计**：连续 2 次失败才告警，单次失败不告警 ——
> 单次失败可能是网络抖动 / GC pause / 拨测节点临时问题，
> 连续 2 次（间隔 1min）失败说明大概率真的有问题。

### Step 4 — 创建第二条监控（浅检查，成本: 0）

任务名 `<app>-prod-shallow`，地址 `/api/health`（浅检查，进程活着就 200），其他配置同上。

**为什么要两条**：
- `/api/health` 永远返回 200（只要进程活着）
- `/api/health/deep` DB 挂时返回 503

对照两条的结果就能快速定位故障层：

| shallow | deep | 判断 | 先查 |
|---|---|---|---|
| 200 | 503 | 进程活着但 DB 连不上 | 数据库 / 网络 |
| fail | fail | 进程挂了 / 反代挂了 | 进程管理器 / 反代 |
| 200 | 200 但用户报障 | 业务层问题，黑盒拨测覆盖不到 | 需补业务级 SLO 监控 |

## 三、告警接收配置

> 原则：**告警直推个人手机，不混进任何工作群**——告警和工作消息混在一起的结果是两边都被忽略。

### 选一个能直达你手机的通道

不依赖任何企业 IM 后台配置（很多公司把内部群机器人 / 自定义机器人禁掉了）。挑一个能 5 秒级推到你手机的通道：

1. **能直推个人手机的推送服务**（绑定个人微信「服务通知」/ 手机 push 类）—— 不依赖企业 IM，最省事
2. **群机器人 webhook**（Slack / 飞书 / 钉钉 / 企微自定义机器人）—— 公司允许群机器人时用

通用配置（生产 `.env`）：
```
NOTIFY_CHANNEL=<serverchan|slack|dingtalk|wework|...>
NOTIFY_WEBHOOK_URL=<你的 webhook / push URL>
NOTIFY_WEBHOOK_SECRET=<加签 secret，没有就留空>
```

把同一个 `NOTIFY_WEBHOOK_URL` 配到本 SOP §二 Step 3 的报警规则里（拨测服务告警渠道选「自定义 webhook」，URL 填上即可）。

收尾两件事：
- **手机对该通道开启声音提醒**（微信「服务通知」/ IM 群「强提醒」），告警来时手机会响
- 确认通道**有免费额度且够用**（生产告警频次本来就该 < 1 次/天）

> 备注：群机器人入口在某些企业 IM 后台默认被禁，看到入口不代表能用——先发一条测试消息确认能到手机，再依赖它。

## 四、自测：故意制造一次告警

> 配完不演练 = 不知道告警是否真的能到手机。**第一次配完必须主动测一次。**

### 测试方法 A：直接 stop 服务（推荐，不影响数据）
```bash
ssh <prod-host>
pm2 stop <app>            # 或 systemctl stop <service>
# 等待 3-5 分钟（连续 2 次拨测失败）
# 手机应该收到告警
pm2 start <app>          # 或 systemctl start <service>
# 等 1-2 分钟应该收到「恢复」告警
```

记录：从 stop 到手机响铃的实际时长。**预期时长取决于你 §二 Step 2 填的拨测粒度**：1min 粒度 → ≤ 6 分钟（2 个 1min 监控周期 + 处理延迟）；5min 粒度 → ~10 分钟（2 个 5min 周期 + 处理延迟）。按你实际填的粒度对照，别拿 1min 的预期去要求 5min 的档。

### 测试方法 B：制造 DB 不可达（更接近真实故障）
临时把生产 `.env` 的 `DATABASE_URL` 改成无效连接串 → reload 应用（`pm2 reload <app>` / `systemctl restart <service>`）
- `/api/health` 仍 200（进程活着）
- `/api/health/deep` 应返回 503
- 拨测连续 2 次 fail → 告警

⚠️ **测完立刻改回去**，否则生产挂着。

### 验证清单
- [ ] 手机响铃了
- [ ] 告警内容能看出是哪个端点失败
- [ ] 告警时间戳与故障时间一致
- [ ] 服务恢复后 5min 内收到「恢复」通知
- [ ] 通道告警消息没有被静默掉（检查手机该通道的声音/通知设置）

任一条不通过就立即排查配置，不要带病上线。

## 五、与应用层告警的分工

| 告警来源 | 触发条件 | 渠道 | 备注 |
|---|---|---|---|
| 外部黑盒拨测 | `/api/health/deep` 连续 2 次 503 或超时 | `NOTIFY_WEBHOOK_URL` | **本 SOP**，覆盖所有「假活」场景 |
| 错误监控（如 Sentry） | 应用层 5xx 异常、未捕获错误 | 错误监控自带渠道（与告警群独立） | 错误监控，不替代拨测 |
| 进程退出钩子（uncaughtException） | Node 进程崩溃 | `NOTIFY_WEBHOOK_URL` | 在 server 入口注册 |
| 数据库备份失败事件 | 备份任务失败 | `NOTIFY_WEBHOOK_URL` | 见 [`./backup-recovery-sop.md`](./backup-recovery-sop.md) §一 |
| 云服务器主机监控 | CPU > 80% 持续 5min / 内存 > 90% / 磁盘 > 85% | `NOTIFY_WEBHOOK_URL` | 控制台 → 主机监控 |

**分工逻辑**：
- 拨测 = 黑盒，从外部看服务能不能用
- 错误监控 = 白盒，看代码里发生了什么异常
- 进程管理器 = 进程级，看进程本身的生命周期
- 数据库 / 主机 = 基础设施级，看资源是否健康

四层互补，缺一层都有可能漏。

## 六、报警值班与降噪

solo 阶段所有告警都到你一个人手上。要避免告警疲劳：

- **真告警必须能立刻响应**：手机长时间不在身边时（开会、睡觉），告警依然要响
- **假告警必须立刻调阈值**：每次假阳性后回到这个 SOP，调高静默期 / 失败阈值 / 增加探测点
- **每月复盘**：检查上月告警次数、真假比例、平均响应时间，记录进运维日志

经验值：
- 月告警 0 次 → 监控可能没真生效，主动测一次
- 月告警 1-3 次（真告警） → 健康
- 月告警 ≥ 5 次 → 服务稳定性有问题，要排查根因，不是调阈值
- 月告警 ≥ 10 次（含假告警） → 阈值设错了，要降噪

每月体检节奏并入 [`../cadence/weekly-check.md`](../cadence/weekly-check.md) 的月度回顾。

## 七、未来扩展（团队 ≥ 2 人后）

- 告警轮值排班（PagerDuty 等）

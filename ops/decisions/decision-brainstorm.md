# 多视角决策 workflow（decision-brainstorm）

> 治理方法论 **S11** 的可执行模板。
> 一句话：关键决策别让 AI 一上来就给一个"四平八稳的中庸答案"——先逼它从多个**真分歧**视角并行发散，再对抗验证剔掉伪缺口，最后收敛成你能拍板的 2-4 个选项。

`decision-brainstorm.js` 是这个 workflow 的代码实现；本文件讲**怎么用、什么时候用**。

---

> ⚠️ **先看这个：`decision-brainstorm.js` 不是能直接 `node` 跑的 CLI 脚本。**
>
> 它是一段 **Workflow 编排模板**——写给 **Claude Code 的 Workflow 工具 / 类似的 multi-agent 编排器**用的。它依赖编排运行时才存在的 `args` / `agent()` / `pipeline()` / `phase()` / `log()` 这些注入函数，文件顶部还直接 `return`——本 kit 里**不带这个运行时**，所以你 `node decision-brainstorm.js` 一定会报错，这是预期的，不是 bug。
>
> 怎么用：
> 1. **有支持该编排的环境**（如 Claude Code 的 Workflow 工具）→ 把它作为 workflow 模板加载运行；
> 2. **没有** → 把它当**伪代码 / 流程参考**，照着三段式（发散 → 验证 → 收敛）**自己手动落地**：开 N 个视角各自发散，逐条 Read/Grep 真实材料验证剔伪缺口，最后人工收敛成 2-4 个候选 + 推荐。
>
> 下面「例子」里的 `decision-brainstorm(...)` 写法，是**在编排器里如何起这个 workflow**（传什么参数），**不是命令行能直接敲的命令**。

---

## 它解决什么问题

AI 单轮回答关键决策时有两个老毛病：

1. **过早收敛**——还没把真正对立的考量摆出来，就给了一个看似全面、实则和稀泥的方案。
2. **拍脑袋当结论**——把"项目其实已经做了的东西"误报成缺口，把没核实的猜测当事实写进建议。

这个 workflow 用**三阶段**把这两个毛病挡住：

```
Diverge（发散）          Verify（验证）              Converge（收敛）
多个真分歧视角并行   →   逐条 Read/Grep 真实材料   →   去重 + 排序，给决策者
各自给独立判断、         判 verified/partly/          2-4 个候选 + 带理由推荐
论点、风险、提案         refuted/unverifiable         + 保留少数异见 + 拍板区
```

- **Diverge**：每个视角是一个独立 agent，被明确要求"制造有价值的分歧"，而不是附和。默认 6 个视角：架构师 / PM·业务 / 批判者(红队) / 安全·合规 / 运维·可观测 / 简单性。
- **Verify**：发散容易飘，所以每个视角发完立刻配一个验证 agent，**实际读文件**核对每条论点，把"项目其实已有"的伪缺口标 `refuted` 剔除。这是 S11 的命门。
- **Converge**：只采信验证站得住的论点，跨视角去重，把分歧显式摆出来，收敛成候选方案 + 带理由的推荐 + 给决策者的拍板区（含 `[NEEDS CLARIFICATION]` 标记）。

每阶段输出受 **JSON schema** 约束（`DIVERGE_SCHEMA` / `VERIFY_SCHEMA`），保证论点都带 `evidence`、验证都带 `verdict`——逼 AI 给证据而不是空话。

---

## 什么时候用

值得花这套流程的，都是"想错了要返工、甚至上线翻车"的决策点：

| 场景 | 典型问题 |
|------|---------|
| **需求定稿** | 这个功能到底做不做、做到什么边界、和现有流程怎么衔接 |
| **技术架构选型** | 选哪个方案、要不要引入新依赖/新服务、可不可逆 |
| **安全/合规审计** | 这个改动会不会绕过权限、泄漏数据（多租户项目尤其盯隔离） |
| **疑难 bug 根因** | 同一个 bug 修第 3 次还在出，多半方向错了——用多视角重审根因 |
| **复盘 / 规范自审** | 事故复盘、现有规范是否还成立 |

**不值得用的场景**：改字段、调样式、修单点 bug 这类小改动——直接做，别套流程。

## 怎么用

### 调用参数

`args` 可以是一个字符串（就是决策问题），或一个对象：

| 字段 | 必填 | 说明 |
|------|------|------|
| `question` | ✅ | 一句话讲清要定什么 |
| `materials` | 选 | 现有材料/文件路径/事故时间线，供验证阶段 Read/Grep 核实现状 |
| `scale` | 选 | `'medium'`（3 视角）/ `'large'`（默认，6 视角 + 对抗验证） |
| `lenses` | 选 | 自定义视角数组，元素 `{key, focus}` 或字符串；不传走默认 |

### 例子

> 下面是**在编排器里如何起这个 workflow**（传给它什么 `args`），不是能直接 `node` 跑的命令行。换成你那套编排器的调用语法即可。

```js
// 最简：只给问题，走默认 6 视角
decision-brainstorm("要不要把通知系统从轮询改成 WebSocket？")

// 带材料和自定义视角
decision-brainstorm({
  question: "新订单导出功能，CSV 还是 Excel，要不要异步队列？",
  materials: "server/services/export.js, docs/prd/order-export.md, 上次导出超时事故时间线",
  scale: "large",
  lenses: [
    { key: "性能", focus: "大数据量导出的内存/超时风险" },
    { key: "PM/业务", focus: "用户真实使用频率和数据量级" },
    "简单性",
  ],
})
```

### 输出怎么落地

收敛简报结尾会带"拍板区"。决策定了之后：

- **需求类决策** → 填进对应 PRD 的决策清单段落
- **架构类决策** → 落一份 ADR（架构决策记录）

这样下次有人问"当初为什么这么选"，有据可查，不用重新吵一遍。

## 与治理体系的关系

- 对应治理方法论 **S11**（关键决策多视角头脑风暴）。
- 验证阶段强制"读真实材料、附 file:line 证据"，和**防漂移原则**（凭证据不凭印象）同源。
- 安全视角默认盯权限/数据隔离，呼应项目安全红线（多租户项目把"租户隔离"作为该视角的专属硬约束）。

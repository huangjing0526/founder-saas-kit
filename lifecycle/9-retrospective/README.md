# 复盘与经验沉淀（交付后闭环）

> 产品生命周期第⑨阶段。前面八个阶段把一个需求从发现做到上线，这一阶段把「上线之后学到的东西」喂回前面八个阶段——让同一个坑不会被反复踩。

---

## 在生命周期里的位置

```
⓪ 竞品 → ① 需求 → ② PRD → ③ UI 基线 → ④ 架构 → ⑤ 编码
   → ⑥ 测试 → ⑦ 上线 → ⑧ 运营 → ⑨ 复盘与经验沉淀
                                       │
        └──────────────── 喂回 ⓪~⑧（不是终点，是回路）──────────────┘
```

复盘不是流程的尾巴，是**回路**。每一次返工、事故、踩坑，都是一次「前面某个阶段漏了一道防线」的信号。本阶段的工作就是：把这个信号**焊回**对应阶段的可执行载体（规则表 / 事故索引 / 机检脚本 / 行为 skill），让下一次同类问题在更早的阶段就被挡住。

---

## 解决什么问题

一句话：**把每次返工 / 事故 / 踩坑，变成一条可复用的规则、检查或 skill，而不是同一个坑反复踩。**

反面教材（本阶段要消灭的）：

- 同一类 bug 这个月修一遍、下个月又修一遍——因为根因从没被沉淀，只在脑子里。
- 复盘开了、文档写了，但写完就躺在某个角落，没人记得、没接进任何流程——**只写文档不焊进流程的经验会腐烂**。
- 「我记得上次有个坑」——靠人记 = 早晚忘。能机检的，就该写成脚本而不是靠人脑。

呼应两条核心方法论原则：

- **「同一个问题修到第 3 次还在出 → 立刻停下，方向大概率错了」**——第 3 次复发不是「再修一次」的信号，是「该把它升级成结构性防线」的信号。本阶段就是承接这个升级动作的地方。
- **「能机检的不靠人记」**（防漂移方法论原则③）——沉淀的终点不是一篇散文，是一个能跑、会失败、能挂进 CI 的载体。

---

## 沉淀去向：四个落点（闭环到已有资产）

复盘的产出**必须落到一个可执行载体**，不能只停在「我们以后注意一下」。根据这次教训的性质，落到下面四个之一（可同时落多个）：

| # | 教训性质 | 落点 | 形态 |
|---|---------|------|------|
| ① | 一条新的业务规则 / 自动行为 / 硬编码常量 | [`../../engineering/registries/business-rules-registry.template.md`](../../engineering/registries/business-rules-registry.template.md) | 登记一条 `{MODULE}-{V/A/C/F/P}-{NNN}`，附 `file:line` |
| ② | 一次事故 / 反复出现的根因 | [`../../engineering/methodology/pitfall-index.template.md`](../../engineering/methodology/pitfall-index.template.md) | 登记一条 `<CATEGORY>-<NNN>`，写清根因+防止复发，标 Systemic |
| ③ | 能被机器检查出来的（结构 / 隔离 / i18n / 漂移） | [`../../engineering/quality-scripts/`](../../engineering/quality-scripts/) | 写成 `check-*.cjs` + 接进 `health-audit.cjs`（月度健康度审计） |
| ④ | 一条该固化的行为纪律（AI / 团队该怎么做） | 新 skill 或 [`../../engineering/governance-skills/`](../../engineering/governance-skills/) | 按 8 段式写 skill，或补进既有 skill |

**判断顺序（从强到弱）**：能机检的优先走 ③（机器永远比人靠谱）；机检不了但是结构性根因走 ②；属于业务约束走 ①；属于「人/AI 该怎么做」的纪律走 ④。一条教训常常同时落两处——比如「软删除漏清唯一键」既进 ②（pitfall 索引）又进 ③（写个 `check-*` 扫所有软删除实体）。

> **铁律**：复盘报告里每一条教训，必须在「沉淀去向清单」里逐条标明落到了 ①②③④ 的哪一个、对应哪个文件 / 哪条 ID。没有落点的教训 = 没沉淀，等于没复盘。

---

## 和「运营 / 监控阶段」（⑧）的衔接

- **⑧ 运营 / 监控**回答「系统现在到底跑得好不好、有没有做 X」——审计类排查先读文件验证、附 `file:line` 证据、再下结论（审计先验证后报告，即 S9 的事）。
- **⑨ 复盘**承接运营 / 审计 / 事故里暴露的问题，把它**焊成防线**，让下次审计能用脚本一键查、而不是靠人逐行读。

两者构成闭环：运营 / 审计发现的「能机检项」→ 复盘把它写成 `check-*` → 下个月审计直接跑脚本 → 覆盖面越来越大、靠人记的越来越少。

## 怎么用

1. 一次迭代 / 事故 / sprint 结束 → 复制 `retro-template.md` 填一份。
2. 填到「沉淀去向清单」时，对每条教训按 ①②③④ 决定落点，**当场就落**（不是「回头再说」）。
3. 同一问题已经是第 2-3 次出现 → 触发 `experience-capture` skill，强制做根因分析 + 升级成结构性防线。
4. 能机检的，写成 `../../engineering/quality-scripts/check-*.cjs` 并接进 `health-audit.cjs`，下次自动跑。
